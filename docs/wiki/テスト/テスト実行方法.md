# テスト実行方法

プロジェクトのテスト種別ごとの実行コマンドと前提条件。

## 前提

- Python 3.12 以上 + uv
- 設定: `~/.config/ai-monitor/settings.yaml`（`settings.yaml.example` をコピーして作成）
- 環境差分は `settings.{環境}.yaml` に書き、環境名は環境変数 `AI_MONITOR_ENV`（または起動引数 `--env`）で指定

## E2E テスト

実モニター（サブプロセス）+ 実 LLM（tmux 上の Claude Code）+ sandbox の実 GitHub リポジトリで実行。
対象は `設計図/シナリオ/` の各ファイルと 1:1（各ファイル冒頭の対応テストファイル）。

**前提:**

- `~/.config/ai-monitor/settings.e2e.yaml` に sandbox 用の設定（キーは `設計図/設定/モニター.md` 参照）
- `AI_MONITOR_ENV=e2e` を付与し、`AI_MONITOR_WIKI_BASE` / `WIKI_BASE` は外して実行する（SessionStart フックが展開した値が設定ファイルより優先されるため）
- モニターは全テストで **1 プロセスを共有**する（本番と同じ「1 プロセスが全対象を監視する」構成）。pid / ロック / セッション台帳は `.e2e/` に置き、前回の残骸は実行開始時に停止する
- 待受ポートが空いていること（テスト管理外のプロセスが占有している場合は起動時に失敗する）
- 誤実行防止のため `--run-e2e` フラグ必須（フラグなしだと skip される）
- 検証用の Issue / PR / ブランチ / worktree / tmux セッションは fixture が作成し、テスト後に片付ける

**実行前の確認:**

- 両クローン（ai-monitor / sandbox）の作業ツリーが、読ませたい内容になっていること
- `config/agent_phases.yaml` に載っている全フェーズページが実在すること
- 待受ポートが空き・tmux セッションなし・sandbox に open の Issue / PR なし
- `plugins/` を変更した場合は、その反映が済んでいること（変更の届き方が 3 経路に分かれる）

| 変更対象 | 反映経路 | プラグイン更新 |
| --- | --- | --- |
| `docs/wiki/` のフェーズ・規約 | モニターがローカルクローンから直読み | 不要 |
| `src/` のモニター実装 | E2E が `PYTHONPATH=src` で直接起動 | 不要 |
| `plugins/` のフック・注入スクリプト・定数 | エージェントセッションがプラグインキャッシュから読む | 必要 |

**実行後の確認:**

エージェントの挙動は Claude Code が会話ログ（jsonl）に自動で残す。
保存先は `~/.claude/projects/{CWD をハイフン化したもの}/*.jsonl` で、ツール呼び出し・応答・エラーの全履歴が入る。
OTel を有効にしている場合は `ai_monitor.number` / `ai_monitor.agent` 属性で対象ごとに絞り込める。

pass / fail に関わらず必ず jsonl を確認する。
assert が通っただけでは気づけない副作用や、エージェントが自力でリトライして隠れた手順書の誤りが潜んでいるため。
少なくとも次の 3 点を機械的に見る。

```bash
latest=$(ls -t ~/.claude/projects/{プロジェクトのログディレクトリ}/*.jsonl | head -1)
grep -oE '"name":"mcp__[^"]*' "$latest" | sort | uniq -c    # MCP ツールが正しい名前で呼ばれているか
grep -c 'is_error":true' "$latest"                            # ツールエラーが混入していないか
grep -oE 'InputValidationError[^"]*' "$latest" | head -3      # 引数不足・型不一致がないか
```

**全件実行:**

```bash
env -u AI_MONITOR_WIKI_BASE -u WIKI_BASE AI_MONITOR_ENV=e2e uv run pytest tests/e2e/ --run-e2e -n 4
```

**個別シナリオ実行:**

```bash
env -u AI_MONITOR_WIKI_BASE -u WIKI_BASE AI_MONITOR_ENV=e2e uv run pytest {シナリオテストファイルパス} --run-e2e
```

`-n` の並列度は同時に走る tmux セッション数（= 同時起動する Claude Code の数）を決める。

## 結合テスト（フロント）

なし

## 結合テスト（バック）

pytest で実行。

**前提:**

- GitHub API（githubkit）/ モニター HTTP は Mock 化（実 API は叩かない）
- 対象は `設計図/バックエンド結合/` の詳細ファイルと 1:1（各ファイル冒頭の対応テストファイル）

**全件実行:**

```bash
uv run pytest tests/integration/
```

**個別ツール実行:**

```bash
uv run pytest {結合テストファイルパス}
```

## 単体テスト（フロント）

なし

## 単体テスト（バック）

pytest で実行。DB / API 依存なし。

**前提:**

- ファイル外 / プロセス外の依存は Mock（一時 git リポジトリ・実 tmux を使うテストは fixture が作成 / 破棄）
- 対象は `設計図/モジュール構成/**` の単体テスト表と 1:1

**全件実行:**

```bash
uv run pytest tests/unit/
```

**個別ファイル実行:**

```bash
uv run pytest {単体テストファイルパス}
```

## 外部疎通テスト

**実 API（GitHub）に接続して疎通を確認** するテスト。
sandbox（`shuhei1101/ai-monitor-e2e`）への書き込みという副作用があるため **通常の CI では実行しない**。

**前提:**

- `~/.config/ai-monitor/settings.e2e.yaml` に sandbox 用の `github_token` と sandbox プロジェクト（`repo` / `local_path`）を設定（キーは `設計図/設定/モニター.md` 参照）
- `AI_MONITOR_ENV=e2e` を付与して実行する（PAT・対象プロジェクトが sandbox 向けに切り替わる）
- fixture が CWD を sandbox プロジェクトの `local_path` へ切り替える（MCP ツールの対象リポジトリは CWD の git remote から解決されるため）
- 検証用の Issue / PR / ラベル / ブランチは fixture が作成し、テスト後にクローズ / 削除する
- 誤実行防止のため `--run-external` フラグ必須（フラグなしだと skip される）
- テスト対象と確認観点は `設計図/モジュール構成/MCP/GitHub操作.md` の各ツールの `#### 疎通テスト` 表を参照

**全件実行:**

```bash
AI_MONITOR_ENV=e2e uv run pytest tests/external/ --run-external
```

**個別実行:**

```bash
AI_MONITOR_ENV=e2e uv run pytest {外部疎通テストファイルパス} --run-external
```
