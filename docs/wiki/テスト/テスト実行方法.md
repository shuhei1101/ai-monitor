# テスト実行方法

プロジェクトのテスト種別ごとの実行コマンドと前提条件。

## 前提

- Python 3.12 以上 + uv
- 設定: `~/.config/ai-monitor/settings.yaml`（`settings.yaml.example` をコピーして作成）
- 環境差分は `settings.{環境}.yaml` に書き、環境名は環境変数 `AI_MONITOR_ENV`（または起動引数 `--env`）で指定

## 非機能要件テスト

未確定（`設計図/非機能要件.md` が未作成で、実測対象になる決定値がまだない）。

外部システム（GitHub API）への疎通確認は `## 外部疎通テスト` を参照。

## E2E テスト

実モニター（サブプロセス）+ 実 LLM（tmux 上の Claude Code）+ sandbox の実 GitHub リポジトリで実行。
対象は `設計図/シナリオ/` の各ファイルと 1:1（各ファイル冒頭の対応テストファイル）。

**前提:**

- `~/.config/ai-monitor/settings.e2e.yaml` に sandbox 用の設定（キーは `設計図/設定/モニター.md` 参照）
- `AI_MONITOR_ENV=e2e` を付与し、`AI_MONITOR_WIKI_BASE` / `WIKI_BASE` は外して実行する（SessionStart フックが展開した値が設定ファイルより優先されるため）
- モニターは全テストで **1 プロセスを共有**する（本番と同じ「1 プロセスが全対象を監視する」構成）。pid / ロック / セッション台帳は `.e2e/` に置き、前回の残骸は実行開始時に停止する
- 待受ポートが空いていること（テスト管理外のプロセスが占有している場合は起動時に失敗する）
- 誤実行防止のため `--run-e2e` フラグ必須（フラグなしだと skip される）
- ai-monitor の Wiki は実クローンを直読みする。手順書を直すとその場で次のエージェント起動に反映される（起動プロンプトはエージェントを起動するたびに組み立て直すため）

**直列オンリーのテスト:**

共有資源（モニターの設定・複製 Wiki）を書き換えるテストは、他テストと同時に走らせてはいけない。
該当するテストには `serial` マーカーを付け、並列度なしで別に回す。

| マーカー | 意味 | 実行方法 |
| --- | --- | --- |
| なし | 並列実行してよい（既定） | `-n 4` |
| `serial` | 共有資源を書き換えるので単独で走らせる | `-n 0` |
| `defect_report` | 起票先の上書きも要る（`serial` を兼ねる） | `-n 0` + 環境変数の上書き |

`serial` を付ける基準は「モニターの設定または複製 Wiki を書き換えるかどうか」。
壊れた手順書をエージェントに読ませるテスト（`broken_phase_page` を使うもの）が該当する。

並列実行に `serial` のテストが混ざっていると、収集の時点でエラーにして実行を止める。
実行し始めてから気づくと、書き換えの影響を受けた他テストの結果が読めなくなるため。

**後片付け:**

検証用に作ったものは fixture が回収する。
seed した Issue / PR だけでなく、エージェントが動いた結果として増えたものも対象にする。

| 回収するもの | 見つけ方 |
| --- | --- |
| Issue ツリー | seed した Issue から Sub-issue を再帰的に辿る（エージェントが起票した子孫を含む） |
| PR とリモートブランチ | 上記の番号を本文で参照している open PR |
| tmux セッションの対象番号 | 上記の番号を本文で参照している PR 全て（マージ済みを含む。担当エージェントのセッションは PR が閉じても常駐し続ける） |
| 不具合 Issue | 上記の番号を本文で参照している open Issue（親を持たないため Issue ツリーからは辿れない）。起票先を sandbox へ上書きした実行だけが対象で、通常の実行では ai-monitor 側に残す |
| worktree とローカルブランチ | 回収した PR の head ブランチ |
| tmux セッション | 回収した番号に対応するセッション |

順序は セッションの kill → close → 再度 kill → ブランチ削除。
close を先にすると、稼働中のエージェントが head の固定された PR へ操作を続けて 422 になる。
kill だけを先にすると、close までの隙間にポーリングがセッションを起動し直すため、後段でもう一度 kill する。

**実行前の確認:**

- 両クローン（ai-monitor / sandbox）の作業ツリーが、読ませたい内容になっていること
- `config/agent_phases.yaml` に載っている全フェーズページが実在すること
- 待受ポートが空き・tmux セッションなし・sandbox に open の Issue / PR なし
- `plugins/` を変更した場合は、その反映が済んでいること（変更の届き方が 3 経路に分かれる）

| 変更対象 | 反映経路 | プラグイン更新 |
| --- | --- | --- |
| `docs/wiki/` のフェーズ・規約 | モニターがローカルクローンから直読み | 不要 |
| `src/` のモニター実装 | E2E が `PYTHONPATH=src` で直接起動 | 不要 |
| `plugins/` のフック・注入スクリプト・定数 | エージェントセッションがプラグインキャッシュから読む | 必要 |

**実行後の確認:**

エージェントの挙動は Claude Code が会話ログ（jsonl）に自動で残す。
保存先は `~/.claude/projects/{CWD をハイフン化したもの}/*.jsonl` で、ツール呼び出し・応答・エラーの全履歴が入る。
OTel を有効にしている場合は `ai_monitor.number` / `ai_monitor.agent` 属性で対象ごとに絞り込める。

エージェントが手順どおりに進められなかった事象は、実行中に ai-monitor へ不具合 Issue として起票される。
テストが pass していても起票されていることがあるため、実行後に必ず一覧を見る。

```bash
gh issue list --repo shuhei1101/ai-monitor --label "AI不具合報告" --state open
```

OTel も `success=false` で絞って見る。
テストが pass していても拾えていない不具合が出てくる（MCP に拒否された操作・GitHub API の一時エラーからのエージェント自力リカバリ 等）。
`ai_monitor_agent` / `ai_monitor_number` / `ai_monitor_project` 属性で対象ごとに絞り込める。

pass / fail に関わらず必ず jsonl を確認する。
assert が通っただけでは気づけない副作用や、エージェントが自力でリトライして隠れた手順書の誤りが潜んでいるため。
少なくとも次の 3 点を機械的に見る。

```bash
latest=$(ls -t ~/.claude/projects/{プロジェクトのログディレクトリ}/*.jsonl | head -1)
grep -oE '"name":"mcp__[^"]*' "$latest" | sort | uniq -c    # MCP ツールが正しい名前で呼ばれているか
grep -c 'is_error":true' "$latest"                            # ツールエラーが混入していないか
grep -oE 'InputValidationError[^"]*' "$latest" | head -3      # 引数不足・型不一致がないか
```

**全件実行（並列）:**

```bash
env -u AI_MONITOR_WIKI_BASE -u WIKI_BASE AI_MONITOR_ENV=e2e \
  uv run pytest tests/e2e/ --run-e2e -n 4 -m "not serial and not defect_report"
```

**直列オンリーの実行:**

```bash
env -u AI_MONITOR_WIKI_BASE -u WIKI_BASE AI_MONITOR_ENV=e2e \
  uv run pytest tests/e2e/ --run-e2e -m "serial"
```

複製 Wiki（`.e2e/wiki`）はこの実行のときだけ作られ、テストごとに元へ戻る。

**個別シナリオ実行:**

```bash
env -u AI_MONITOR_WIKI_BASE -u WIKI_BASE AI_MONITOR_ENV=e2e uv run pytest {シナリオテストファイルパス} --run-e2e
```

**不具合報告の実行:**

`defect_report` マーカーの付いたテストは、起票されるものがテストデータなので起票先を sandbox へ上書きして別実行する。
複製 Wiki のページ差し替えが他テストからも見えるため直列で回す。

```bash
env -u AI_MONITOR_WIKI_BASE -u WIKI_BASE AI_MONITOR_ENV=e2e \
  AI_MONITOR_REPO=shuhei1101/ai-monitor-e2e MY_PLUGINS_REPO=shuhei1101/ai-monitor-e2e \
  uv run pytest tests/e2e/ --run-e2e -m "defect_report"
```

`AI_MONITOR_REPO` が不具合 Issue とモニター側のルール改修 Issue の、`MY_PLUGINS_REPO` がプラグイン側のルール改修 Issue の起票先を上書きする。
両方を sandbox に向けるため、どちらのツールを選んだかは起票された本文の `## 対象ルール` のページパスで判定する。

`-n` の並列度は同時に走る tmux セッション数（= 同時起動する Claude Code の数）を決める。

**実行の中断:**

ワークフローが停止したときなど、タイムアウトを待たずに打ち切りたい場合は合図ファイルを作る。

```bash
touch .e2e/abort
```

待機中のテストが次のポーリング（15 秒以内）で失敗し、後片付けの fixture がそのまま走る。
合図ファイルは次回の実行開始時に消えるので、消し忘れても次の実行は妨げない。

並列実行中に一部のテストだけ止めたい場合は、合図ファイルに対象を書く。
1 行 1 指定で、テスト ID（`{ファイルパス}::{関数名}`）への部分一致で判定する。
書かれていないテストはそのまま走り続ける。

```bash
echo "test_統合テスト失敗からのバグ修正" > .e2e/abort
```

中身が空なら実行中の全テストが対象になる。
`test_normal` のような複数ファイルに共通する名前を書くと、意図しないテストまで止まる。

プロセスへのシグナルでは止めない。
SIGINT は pytest 本体を終わらせるが、並列実行の worker は後片付けに到達せず、Issue / PR / ブランチ / worktree / tmux セッションが残る。

合図ファイルは待機（`wait_until`）の中でしか読まれないため、worker が GitHub API の応答待ちでブロックしていると届かない。
`.e2e/abort` を置いても進捗（`.e2e/run-*.log` の末尾）が数分変わらない場合は、worker のブロック箇所を確かめる。

```bash
pgrep -P $(pgrep -f "bin/pytest tests/e2e" | head -1) | while read c; do cat /proc/$c/task/*/wchan; echo; done
```

全 worker が `wait_woken`（ソケット読み取り待ち）なら合図ファイルでは止まらない。
このときだけ kill してから、下の順で手で片付ける。

| 手順 | コマンド |
| --- | --- |
| pytest とモニターを止める | 対象 PID へ `kill -KILL` |
| open PR を close + ブランチ削除 | `gh pr close {番号} --delete-branch` |
| open Issue を close | `gh issue close {番号}` |
| 残ったリモートブランチを削除 | `git push origin --delete {ブランチ}` |
| worktree とローカルブランチを削除 | `git worktree remove --force {パス}` + `git branch -D {ブランチ}` |

## 結合テスト（フロント）

なし

## 結合テスト（バック）

pytest で実行。

**前提:**

- GitHub API（githubkit）/ モニター HTTP は Mock 化（実 API は叩かない）
- 対象は `設計図/インターフェース定義/バックエンド/` の詳細ファイルと 1:1（各ファイル冒頭の対応テストファイル）

**全件実行:**

```bash
uv run pytest tests/integration/
```

**個別ツール実行:**

```bash
uv run pytest {結合テストファイルパス}
```

## 単体テスト（フロント）

なし

## 単体テスト（バック）

pytest で実行。DB / API 依存なし。

**前提:**

- ファイル外 / プロセス外の依存は Mock（一時 git リポジトリ・実 tmux を使うテストは fixture が作成 / 破棄）
- 対象は `設計図/モジュール構成/**` の単体テスト表と 1:1

**全件実行:**

```bash
uv run pytest tests/unit/
```

**個別ファイル実行:**

```bash
uv run pytest {単体テストファイルパス}
```

## 外部疎通テスト

**実 API（GitHub）に接続して疎通を確認** するテスト（非機能要件テストのうち外部疎通の分類）。
sandbox（`shuhei1101/ai-monitor-e2e`）への書き込みという副作用があるため **通常の CI では実行しない**。

**前提:**

- `~/.config/ai-monitor/settings.e2e.yaml` に sandbox 用の `github_token` と sandbox プロジェクト（`repo` / `local_path`）を設定（キーは `設計図/設定/モニター.md` 参照）
- `AI_MONITOR_ENV=e2e` を付与して実行する（PAT・対象プロジェクトが sandbox 向けに切り替わる）
- fixture が CWD を sandbox プロジェクトの `local_path` へ切り替える（MCP ツールの対象リポジトリは CWD の git remote から解決されるため）
- 検証用の Issue / PR / ラベル / ブランチは fixture が作成し、テスト後にクローズ / 削除する
- 誤実行防止のため `--run-external` フラグ必須（フラグなしだと skip される）
- テスト対象と確認観点は `設計図/モジュール構成/MCP/GitHub操作.md` の各ツールの `#### 疎通テスト` 表を参照

**全件実行:**

```bash
AI_MONITOR_ENV=e2e uv run pytest tests/external/ --run-external
```

**個別実行:**

```bash
AI_MONITOR_ENV=e2e uv run pytest {外部疎通テストファイルパス} --run-external
```
