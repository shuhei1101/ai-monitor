# ai-monitor テンプレート: PR 本文 / ストーリー

`layer:story` が付いた PR の本文書式。

story PR は **単一ユースケースシナリオを設計するための PR**。
親 story Issue の `## ユースケース要件` を元に、`docs/wiki/設計図/シナリオ/単一ユースケース/{機能名}.md` を作成 / 更新する。
書くのは **タスク一覧（実施すべき To Do）** と **単一ユースケースシナリオテストの結果** だけ（変更内容の詳細は変更ファイル一覧で見る）。

## セクション一覧

| セクション | サブセクション | 必須or条件 | 担当 | 補足 |
| --- | --- | --- | --- | --- |
| `## 紐づく Issue` | - | 必須（PR 作成時） | epic-conductor（PR 作成者） | 起点の intake Issue 番号 |
| `## 概要` | - | 必須 | story-conductor | - |
| `## 背景` | - | 必須 | story-conductor | - |
| `## ユースケース要件` | - | 必須 | story-conductor が草案、ユーザー承認後に確定 | - |
| `## サブシステム一覧` | - | 必須 | story-conductor | 洗い出した subsystem と対応 PR |
| `## タスク一覧` | - | 必須（単一 UC 影響なしで下位へ通過する場合は不要） | story-conductor | Wiki 修正・単一 UC E2E テストの作成 / 実行の To Do。チェックは各行を担当した作業者が入れる |
| `## 単一ユースケースシナリオテスト結果` | - | 必須（テスト実装時にセクション新設 → 実行後に結果記入） | single-scenario-tester | 作成 / 変更した単一 UC E2E テストの結果（新規 + 回帰） |

## `## 紐づく Issue`

### 記述例

```markdown
## 紐づく Issue

- #123 プロフィール編集ストーリー
```

### 補足

- 起点の intake Issue（system レイヤーから始まる場合は立ち上げ Issue）の番号を書く（1 件のみ。階層は base と GitHub のスタック表示で辿る）

## `## 概要`

### 記述例

```markdown
## 概要

ログイン中ユーザーが自身のプロフィール項目（氏名・自己紹介・アバター画像）を編集・保存する。
```

### 補足

- 1 ユースケースを 1〜2 行でまとめる
- 「{アクター} が {何をする}」で書く
- 初回に書いた内容のまま保ち、後から情報を足さない。
  確定した内容は `## 背景` 以降の各セクションに書く（両方に書くと同じ内容を 2 箇所で持つことになる）。
  対象そのものが変わったときだけ既存の記述を書き換える

## `## 背景`

### 記述例

```markdown
## 背景

親 epic #90「プロフィール自己管理機能」の UC「プロフィール編集」に対応。
既存の閲覧機能（`/profile/view`）に対して編集動線を追加する必要がある。
```

### 補足

- 概要と重複しない（概要は「何をするか」、背景は「なぜ必要か」）
- なぜこの story を切り出したか（epic をなぜこの粒度で分けたか）を書く
- **親 epic Issue 番号 + UC 名** の 2 点セットを 1 行入れる（例: `親 epic #90 の UC「プロフィール編集」に対応`）
- **1 story = 1 UC**。
  複数 UC を持つ story は禁止（分割する）

## `## ユースケース要件`

**このユースケース固有の要件**を列挙する。
エピックの `## 横断要件`（全 UC 共通）と役割分担する形。

### 記述例

```markdown
## ユースケース要件

| 要件 | 補足 |
| --- | --- |
| 氏名を編集できる | 50 文字上限 |
| 自己紹介を編集できる | 500 文字上限 |
| アバター画像をアップロードできる | 5MB 上限、JPG/PNG |
| 保存時にバリデーションエラーをインライン表示 | フィールド直下に表示 |
| 同時編集を検知したら警告ダイアログを出す | epic 横断要件「同時編集の検知」に基づく実装 |
| 保存成功時にトーストで通知 | 3 秒表示 |

単一ユースケースへの影響: あり（プロフィール編集の操作手順が変わる）
```

### 補足

**要件列:**
- **ユーザー視点の 1 文** で書く（「{ユーザー} が {アクション} できる / される」）
- 実装用語（API / DB カラム / コンポーネント名）を避ける
- 実装側の詳細（バリデーション具体値・ライブラリ選定 等）は subsystem 側で扱うのでここでは書かない

**補足列:**
- 定数・上限値・振る舞いの追加情報
- 横断要件を参照する行は `epic 横断要件「{要件の要旨}」に基づく` と明記（整合性の起点を残す）

**単一ユースケースへの影響の行:**
- 表の直後に `単一ユースケースへの影響: あり / なし（{根拠}）` の 1 行を置く
- 判定は story-conductor が要件確定で行う（判定フローチャート（レイヤー）の ※3）
- `なし` の場合は単一シナリオ設計を挟まず子 subsystem の起票へ進むため、後続ターンがこの行を読んで経路を決める

**補足:**
- 1 行 = 1 要件。
  条件分岐は補足列 or 別 No に分割
- **横断要件（複数 UC 共通）は書かない**（それは epic 側の `## 横断要件`）
- 本セクションが実装エージェントの実装計画の元になる（1 story だけ読めば完結する状態を維持）

## `## サブシステム一覧`

この UC を実装するために必要な **サブシステム（1 対象システム = 1 subsystem Issue）** を列挙。
単一ユースケースシナリオの結合フローから洗い出し、依存順とあわせて記録する。

### 記述例

```markdown
## サブシステム一覧

| 対象システム | 担当範囲 | 依存 | 対応 subsystem | 補足 |
| --- | --- | --- | --- | --- |
| バックエンド | プロフィール更新 API と入力検証 | なし | #201 | - |
| フロントエンド | プロフィール編集画面と保存導線 | バックエンド | 未起票 | インターフェース確定後に起票 |
```

### 補足

**対象システム列:**
- `scope:*` ラベルに対応する単位で書く（バックエンド / フロントエンド / 外部連携 等）

**担当範囲列:**
- そのサブシステムが持つ責務を 1 行で書く
- 実装詳細（エンドポイント名・DB カラム・コンポーネント名）は対応 subsystem 側の `## システム要件（SA）` に書く

**依存列:**
- 先に確定している必要がある対象システム名。
  依存がなければ `なし`

**対応 subsystem 列:**
- 該当する子 subsystem の Issue 番号（`#xxx` 形式）
- 起票前は `未起票`、起票後にリンクを埋める

**補足:**
- 1 行 = 1 対象システム = 1 subsystem Issue を厳守
- 本表は「story → subsystem の分割マップ」として機能し、依存順の逐次起票の根拠になる

## `## タスク一覧`

### 記述例

```markdown
## タスク一覧

- [ ] `設計図/シナリオ/単一ユースケース/プロフィール編集.md` を新規作成
- [ ] `設計図/シナリオ/README.md` の `## 一覧` に該当行を追加
- [ ] 単一ユースケース E2E テストコードを作成
- [ ] 単一ユースケース E2E テストを実行
```

### 補足

- チェックボックス形式で **やることリスト**を列挙
- 各タスクは 1 行 = 1 To Do とし、1 行を 1 人の担当で完結させる（E2E テストは「作成」と「実行」で担当が分かれるため行を分ける）
- Wiki 修正・テスト作成・テスト実行の 3 種類に分けて書く
- `[x]` はその行の作業をした本人が commit 直後に入れる（指示者は全行チェック済みかを確認するだけ）
- 全行がチェックされてからマージする

## `## 単一ユースケースシナリオテスト結果`

### 記述例

```markdown
## 単一ユースケースシナリオテスト結果

| ファイル | メソッド | 結果 | 補足 |
| --- | --- | --- | --- |
| `tests/e2e/profile_edit.spec.ts` | 全実行 | ✅ | 対応シナリオ: `プロフィール編集` |
```

### 補足

- 本 story で作成 / 変更した単一 UC E2E テストを全て実行して結果を記録
- 結果列: `✅`（pass）/ `❌`（fail）
- 補足列に対応シナリオ名を明記（`docs/wiki/設計図/シナリオ/単一ユースケース/{機能名}.md` と 1:1 対応）
- 単一ユースケースシナリオが無い story はそもそも成立しないが、テスト未整備の暫定 PR なら本文に「なし」と記載
