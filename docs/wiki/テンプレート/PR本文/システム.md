# ai-monitor テンプレート: PR 本文 / システム

`layer:system` が付いた PR の本文書式。

system PR は **プロジェクト全体の構成とエピック分割を確定するための PR**。

親 Issue の `## 構成要件` を満たすように `設計図/アーキテクチャ図.md` と設計ドキュメントの土台を作る PR。
実装コードを含まないため、テスト結果セクションは持たない。

確定した構成は `設計図/アーキテクチャ図.md` が SoT なので本文には転記しない。
追加したファイルも diff で分かるので列挙しない。

## セクション一覧

| セクション | サブセクション | 必須or条件 | 担当 | 補足 |
| --- | --- | --- | --- | --- |
| `## 紐づく Issue` | - | 必須（PR 作成時） | system-conductor（PR 作成者） | 起点の立ち上げ Issue 番号 |
| `## 概要` | - | 必須 | system-conductor | - |
| `## 背景` | - | 必須 | system-conductor | - |
| `## 構成要件` | - | 必須 | system-conductor が草案、ユーザー承認後に確定 | - |
| `## エピック一覧` | - | 必須 | system-conductor が草案、ユーザー承認後に確定 | - |
| `## タスク一覧` | - | 必須 | system-conductor | 土台生成の To Do。チェックは各行を担当した作業者が入れる |

## `## 紐づく Issue`

### 記述例

```markdown
## 紐づく Issue

- #1 TaskFlow の開発基盤立ち上げ
```

### 補足

- 起点の intake Issue（system レイヤーから始まる場合は立ち上げ Issue）の番号を書く（1 件のみ。階層は base と GitHub のスタック表示で辿る）

## `## 概要`

### 記述例

```markdown
## 概要

チーム向けタスク管理ツール「TaskFlow」の開発基盤を立ち上げる。
サブシステム分割・言語・外部システム連携を確定し、設計ドキュメントの土台を作る。
```

### 補足

- 何を立ち上げる / 変えるのかを 1〜3 行でまとめる
- ユーザー入力の範囲内に留める（構成案の中身は `## 構成要件` の領分）
- 初回に書いた内容のまま保ち、後から情報を足さない。
  確定した内容は `## 背景` 以降の各セクションに書く（両方に書くと同じ内容を 2 箇所で持つことになる）。
  対象そのものが変わったときだけ既存の記述を書き換える

## `## 背景`

### 記述例

```markdown
## 背景

現在はタスクを表計算ソフトで管理しており、担当者の変更が共有されず対応漏れが発生している。
社内には既に OTel Collector が稼働しているため、ログ・トレースはそこへ集約したい。
```

### 補足

- 起票に至った経緯・きっかけを整形（ユーザー入力の範囲内）
- 既存の社内資産（監視基盤・認証基盤・デプロイ先）があれば明示する。
  構成の制約になる

## `## 構成要件`

システム全体の構成を決めるための **制約と要求** を列挙する。
決定の結果ではなく、決定が満たすべき条件を書く。

### 記述例

```markdown
## 構成要件

| カテゴリ | 要件 | 補足 |
| --- | --- | --- |
| リポジトリ | 1 リポジトリで完結させる | コード共有のオーバーヘッドを避ける |
| サブシステム | 画面と業務ロジックを別プロセスに分ける | 画面だけを静的配信できるようにする |
| 言語 | バックエンドは Python | 既存の社内資産と揃える |
| 外部システム | 認証は外部 IdP に委譲する | 自前でパスワードを保持しない |
| 外部システム | ログ・トレースは社内 OTel Collector へ送る | 監視を既存基盤に集約する |
| 外部システム | メール送信は外部サービスを使う | 銘柄は不問 |
```

### 補足

**カテゴリ列:**
- `リポジトリ` / `サブシステム` / `言語` / `外部システム` の 4 種類
- 該当する要件が無いカテゴリは行を作らない

**要件列:**
- 「何を満たすべきか」を 1 文で書く。
  銘柄を指定するのはユーザーが明示的に指定した場合だけで、それ以外は満たすべき性質で書く（`認証は外部 IdP に委譲する` であって `Auth0 を使う` ではない）

**補足:**
- 1 行 = 1 要件
- ここが `設計図/アーキテクチャ図.md` の入力になる。
  構成図・サブシステム一覧・外部システム連携の各行が、本表のどれかの要件に対応する状態を保つ

## `## エピック一覧`

プロジェクトを機能単位に分解した epic の構成案。
本表の 1 行が epic PR 1 件になり、`対応 PR` 列が作成の進捗を表す。

新規プロジェクトでは `## 概要` と `## 構成要件` から、既存プロジェクトの移行では実装コードから洗い出す。
分割の判定は `判定フローチャート/エピック分割.md` に従う。

### 記述例

```markdown
## エピック一覧

| エピック | 概要 | 所属ユースケース | 着手順 | 対応 PR | 補足 |
| --- | --- | --- | --- | --- | --- |
| 配信基盤 | 設定読み込みと LLM クライアントの共通処理 | 設定を読み込む / LLM 応答を生成する | 1 | 未作成 | 全 epic が参照するため先頭 |
| コメント応答 | 視聴者コメントへの自動応答 | コメントを取得する / 応答を生成する / 応答を読み上げる | 2 | 未作成 | 配信基盤の完了後 |
| アバター制御 | 応答に合わせた表情・口パクの制御 | 表情を切り替える / 口パクを同期する | 3 | 未作成 | 配信基盤の完了後 |
```

### 補足

**エピック列:**
- ユーザーの目的単位で命名する（画面単位・モジュール単位で切らない）

**概要列:**
- その epic が何を担うかを 1 行で

**所属ユースケース列:**
- 「{対象}を{動詞}する」の 1 動詞句で並べ、` / ` で区切る
- ここに並べた UC 名が、作成後に epic PR の `## ユースケース一覧` へそのまま入る

**着手順列:**
- 1 から始まる連番。
  同じ番号は付けない（並列着手すると共通基盤の設計が衝突するため、必ず直列にする）
- 全 epic から参照される共通基盤の epic を先頭に置く

**対応 PR 列:**
- 作成前は `未作成`、作成後に `#N` を埋める

**補足:**
- 1 行 = 1 epic = 1 epic PR
- 分割の判定は `判定フローチャート/エピック分割.md` に従う
- 着手順で 2 番目以降の epic には `確認:epic-conductor` を付けない。
  先行 epic の完了を見てユーザーが順次付与する

## `## タスク一覧`

### 記述例

```markdown
## タスク一覧

- [ ] `設計図/アーキテクチャ図.md` を新規作成
- [ ] `docs/wiki/` の骨格と各階層の `README.md` を作成
- [ ] `docs/rules.yaml` を空の索引として作成
- [ ] `テスト/テスト実行方法.md` の骨格を作成
- [ ] `外部API/README.md` / `外部ライブラリ/README.md` を空の索引として作成
- [ ] `README.md` の骨格を作成
- [ ] `.gitignore` を作成
- [ ] `.claude/settings.json` にルール索引を宣言
- [ ] GitHub ラベルを作成
```

### 補足

- チェックボックス形式で **やることリスト**を列挙
- 各タスクは 1 行 = 1 To Do
- 作成するファイルのパスを明記する（何を作れば完了かが一意に決まるようにする）
- `[x]` はその行の作業をした本人が commit 直後に入れる（指示者は全行チェック済みかを確認するだけ）
- 全行がチェックされてからマージする
