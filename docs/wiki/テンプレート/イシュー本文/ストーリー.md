# ai-monitor テンプレート: ストーリー

`layer:story` が付いた Issue の本文書式。
1 ユースケース（1 シナリオ）を扱う親 Issue で使う。

story は **「何のユースケースを扱うか」を要件レベルで明示** するのが役割。

1 story = 1 シナリオファイル = 1 E2E テストファイル に 1:1 対応する。

## セクション一覧

| セクション | サブセクション | 必須or条件 | 担当 |
| --- | --- | --- | --- |
| `## 概要` | - | 必須 | story-conductor |
| `## 背景` | - | 必須 | story-conductor |
| `## ユースケース要件` | - | 必須 | story-conductor が草案、ユーザー承認後に確定 |
| `## サブシステム一覧` | - | 必須（子 subsystem 起票時に記入） | story-conductor |

## `## 概要`

### 記述例

```markdown
## 概要

ログイン中ユーザーが自身のプロフィール項目（氏名・自己紹介・アバター画像）を編集・保存する。
```

### 補足

- 1 ユースケースを 1〜2 行でまとめる
- 「{アクター} が {何をする}」で書く

## `## 背景`

### 記述例

```markdown
## 背景

親 epic #90「プロフィール自己管理機能」の UC「プロフィール編集」に対応。
既存の閲覧機能（`/profile/view`）に対して編集動線を追加する必要がある。
```

### 補足

- 概要と重複しない（概要は「何をするか」、背景は「なぜ必要か」）
- なぜこの story を切り出したか（epic をなぜこの粒度で分けたか）を書く
- **親 epic Issue 番号 + UC 名** の 2 点セットを 1 行入れる（例: `親 epic #90 の UC「プロフィール編集」に対応`）
- **1 story = 1 UC**。
  複数 UC を持つ story は禁止（分割する）

## `## ユースケース要件`

**このユースケース固有の要件**を列挙する。
エピックの `## 横断要件`（全 UC 共通）と役割分担する形。

### 記述例

```markdown
## ユースケース要件

| 要件 | 補足 |
| --- | --- |
| 氏名を編集できる | 50 文字上限 |
| 自己紹介を編集できる | 500 文字上限 |
| アバター画像をアップロードできる | 5MB 上限、JPG/PNG |
| 保存時にバリデーションエラーをインライン表示 | フィールド直下に表示 |
| 同時編集を検知したら警告ダイアログを出す | epic 横断要件「同時編集の検知」に基づく実装 |
| 保存成功時にトーストで通知 | 3 秒表示 |

単一ユースケースへの影響: あり（プロフィール編集の操作手順が変わる）
```

### 補足

**要件列:**
- **ユーザー視点の 1 文** で書く（「{ユーザー} が {アクション} できる / される」）
- 実装用語（API / DB カラム / コンポーネント名）を避ける
- 実装側の詳細（バリデーション具体値・ライブラリ選定 等）は subsystem 側で扱うのでここでは書かない

**補足列:**
- 定数・上限値・振る舞いの追加情報
- 横断要件を参照する行は `epic 横断要件「{要件の要旨}」に基づく` と明記（整合性の起点を残す）

**単一ユースケースへの影響の行:**
- 表の直後に `単一ユースケースへの影響: あり / なし（{根拠}）` の 1 行を置く
- 判定は story-conductor が要件確定で行う（判定フローチャート（レイヤー）の ※3）
- `なし` の場合は単一シナリオ設計を挟まず子 subsystem の起票へ進むため、後続ターンがこの行を読んで経路を決める

**補足:**
- 1 行 = 1 要件。
  条件分岐は補足列 or 別 No に分割
- **横断要件（複数 UC 共通）は書かない**（それは epic 側の `## 横断要件`）
- 本セクションが実装エージェントの実装計画の元になる（1 story だけ読めば完結する状態を維持）

## `## サブシステム一覧`

この UC を実装するために必要な **サブシステム（1 対象システム = 1 subsystem Issue）** を列挙。
単一ユースケースシナリオの結合フローから洗い出し、依存順とあわせて記録する。

### 記述例

```markdown
## サブシステム一覧

| 対象システム | 担当範囲 | 依存 | 対応 subsystem | 補足 |
| --- | --- | --- | --- | --- |
| バックエンド | プロフィール更新 API と入力検証 | なし | #201 | - |
| フロントエンド | プロフィール編集画面と保存導線 | バックエンド | 未起票 | インターフェース確定後に起票 |
```

### 補足

**対象システム列:**
- `scope:*` ラベルに対応する単位で書く（バックエンド / フロントエンド / 外部連携 等）

**担当範囲列:**
- そのサブシステムが持つ責務を 1 行で書く
- 実装詳細（エンドポイント名・DB カラム・コンポーネント名）は対応 subsystem 側の `## システム要件（SA）` に書く

**依存列:**
- 先に確定している必要がある対象システム名。
  依存がなければ `なし`

**対応 subsystem 列:**
- 該当する子 subsystem の Issue 番号（`#xxx` 形式）
- 起票前は `未起票`、起票後にリンクを埋める

**補足:**
- 1 行 = 1 対象システム = 1 subsystem Issue を厳守
- 本表は「story → subsystem の分割マップ」として機能し、依存順の逐次起票の根拠になる
