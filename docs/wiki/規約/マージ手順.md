# ai-monitor: マージ手順

配下の PR を base ブランチへマージするときの共通手順。
次の 2 種類で同じ手順を使う。

| 種類 | 例 | 実施者 |
| --- | --- | --- |
| 成果物 PR → レイヤーブランチ | モック / シナリオ / インターフェース定義 / モジュール構成 / テスト / 実装 / RE | その成果物を発注した conductor |
| レイヤー PR → 親レイヤーブランチ | subsystem → story / story → epic / epic → master | そのレイヤーの conductor |

どちらも squash マージなので、成果物ブランチで応答ループの commit が何本積まれても、レイヤーのブランチには 1 コミットに畳まれて載る。

conductor スキルに動的コンテキストとして注入して使う。

## 手順

1. 対象 PR の Draft を MCP `mark_pr_ready` で解除する（Ready 済みなら何も起きない）
2. 対象 PR の worktree に復帰し、base ブランチを取り込む（`git fetch` + `git merge origin/{base}`）
3. コンフリクトがないことを確認する（あれば「コンフリクト時の対応」へ）
4. MCP `merge_pr`（`strategy`: `squash`）で squash マージ + リモートブランチ削除
5. MCP `worktree_remove` でローカルの worktree を削除する

マージした PR がその作業単位の面なので、マージをもって面が閉じる。
Issue を閉じる手順は要らない。

例外は最上位 epic の完了時で、配下の全 epic PR がマージされた時点で起点の intake Issue を MCP `close`（`reason`: `completed`）で閉じる。
昇格マージの base は master ではないため、PR 本文にクローズキーワードを書いても intake Issue は閉じない。

## レイヤーブランチへ直接 commit しない

レイヤーブランチ（system / epic / story / subsystem）に成果物を直接 commit してはいけない。
必ず成果物ブランチを切り、PR を経由して squash マージする（規約『ブランチ戦略』の成果物ブランチ）。

直接 commit すると、ユーザーとの応答ループで積んだ手直しの commit がレイヤーの PR の履歴にそのまま並び、何が成果物なのか読めなくなる。

## コンフリクト時の対応

1. 対象 PR に競合ファイルと「どちらの変更を残すか」の相談コメントを投稿 + `議論中` 付与 + `assignee=ユーザー` 設定
2. 応答ループ: ユーザーの判断コメント + assignee 外し → 指示どおり解消 commit → 解消内容を同スレッドに返信追記（追加の競合・疑問があれば再相談 + `assignee=ユーザー` 再設定）
3. 全競合解消後、手順 4（squash マージ）に合流する
