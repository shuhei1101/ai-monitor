# 規約: フェーズ索引の網羅

フェーズ索引は「上から順に見て最初にマッチしたフェーズを 1 つ実行する」構造のため、待機・終了に相当する状態が索引に無いと、必ず後段のフェーズが誤って選ばれる。
索引はどの状態でも必ず 1 つのフェーズにマッチするように書く。

## 索引に置く順序

起動条件が狭いものから広いものへ並べる。
待機・終了の分岐は、それが成立する状況で後段のフェーズが誤って選ばれないよう、対応するフェーズ群の直後に置く。

## 1 つの面に確認ラベルは 1 つ

確認ラベルは「その面の手番を誰が持っているか」を表す。
一つの面（Issue / PR）に確認ラベルが 2 つ付くと、モニターの起動条件（`確認:*` あり + assignee なし + `処理中:*` なし）を 2 人が同時に満たし、両方が起動する。

受け渡しは `transition_phase` 1 回で「自分の `確認:{自分}` を外して相手の `確認:{相手}` を付ける」形にする。
外さずに付ける・付けてから別の呼び出しで外す、のどちらもしない。

別の面へ依頼するときも同じで、依頼先の面に `確認:{依頼先}` を付けたら、自分が確認ラベルを持っている面からそれを外す。
依頼中に自分の確認ラベルを残すと、毎周期そのラベルで起動し続ける（待機の分岐にマッチしても外れるのは `処理中:{自分}` だけなので、次の周期でまた起動条件を満たす）。
復帰は、依頼先が完了報告で付け直す確認ラベルで行う。

一つの面を複数のエージェントが順に使うのは構わない（subsystem PR を architect → tester → implementer が順に持つ）。
同時に 2 人が持たないことだけを守る。

## 待機と終了の使い分け

| 状況 | 扱い | ラベル操作 |
| --- | --- | --- |
| ユーザーの応答を待っている | 待機 | `議論中` 付与 + `assignee=ユーザー` 設定。`確認:{自分}` は保持する |
| 依存先の Issue が open で着手できない | 待機 | `確認:{自分}` を保持し、`処理中:{自分}` だけを外す |
| 対象が closed で、もう自分にできることがない | 終了 | `確認:{自分}` と `処理中:{自分}` の両方を外す |

待機は「状況が変わったターンで正しいフェーズから再開する」ことが前提なので、確認ラベルを外さない。
終了は再開しないので確認ラベルも外す。

ユーザー待ちの待機で確認ラベルを保持してよいのは、`assignee=ユーザー` が付いていてモニターが起動しないため（面の確認ラベルも 1 つのまま）。
依頼先の作業待ちは待機にあたらない。
手番ごと相手へ渡してあるので確認ラベルが手元に無く、そもそも起動しない。

## 待機・終了の分岐でやらないこと

依存先待ちの待機と closed 検知の終了は、状態を進めずにその場で自ターンを終える分岐にあたる。

- 対象の本文を変更しない
- コメントを投稿しない（ユーザーの判断を求める場面ではない）
- 下位エージェントへのラベル付与・タスク割り当てをしない

例外は closed 検知時の確認 / 処理中ラベルの除去だけ。
ユーザー待ちの待機はこれに含まれない（相談・提案コメントを投稿したうえで応答を待つ分岐のため）。

## 依存先が残っているとき

Issue 間の依存は GitHub の blocked by で表す（`設計図/インターフェース定義/バックエンド/依存設定.py.md`）。
初期処理で取得した `blocked_by` に `OPEN` の Issue が残っている間は、その Issue に着手しない。

依存が残っている場合は待機として扱い、`確認:{自分}` を保持したまま `処理中:{自分}` だけを外す。
依存先が close されたターンで通常のフェーズ判定に戻る。

親子関係（epic → story → subsystem）は Sub-issue リンクが持つため、blocked by には現れない。
親の完了を待つ必要はなく、親が open のままでも子は進めてよい。

## closed 対象で起動したとき

モニターは open の対象しか起動しないが、一覧を取得した後に close された対象は同じ周期で起動しうる。
初期処理で対象が closed だと分かった場合は、着手せず確認 / 処理中ラベルを外して終了する。

セッションの解放とラベル除去はモニター側でも行う（`設計図/インターフェース定義/バックエンド/個別解放.py.md`）。
エージェント側の終了分岐は、解放が走る前の周期で起動してしまった場合の受け皿にあたる。

## 索引に無い状態が見つかったとき

未解決の自分宛コメントがある場合は、索引末尾の『問い合わせ応答』で内容に答えて手番を返す。
進捗の状況確認・他エージェントからの引き継ぎ・単発の質問など、既存の工程に当てはまらない依頼を受ける口になる。

コメントも無い状態で該当分岐が見つからない場合は、後段のフェーズへフォールスルーさせずに不具合として報告する（共通ルール『不具合の報告』）。
報告したうえで待機として自ターンを終える。
