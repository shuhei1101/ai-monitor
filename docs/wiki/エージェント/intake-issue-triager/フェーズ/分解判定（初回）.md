# 分解判定（初回）

対象 Issue が既存の作業と重複していないかを確かめ、重複していなければ内容を作業単位に分解し、分解案 + 確認質問を投稿して待機に入る。

## 手順

### 関連情報の調査

本文から機能名・画面名・エラーメッセージなどのキーワードを抽出し、重複の判定・分解・確認質問の材料になる既存情報を集める。

- 関連 Issue / PR: MCP `search_issues_and_prs` をキーワードごとに呼び（`query`: キーワード + `is:open`。`is:issue` / `is:pr` 等の修飾子も可）、依存・重複しそうな番号と概要を控える
- 既存の報告: 対象 Issue に `$AI_MONITOR_LABEL_AI_DEFECT_REPORT` の値が付いている場合、続けて MCP `search_issues_and_prs` を呼ぶ（`query`: `label:"{そのラベル値}" is:issue is:open`）

`search_issues_and_prs` は指定しなければ closed も返す。
統合先になれるのは open のものだけなので、検索クエリに `is:open` を必ず含める。
- 既存設計: 注入済みのシナリオ索引（`設計図/シナリオ/README.md`）から関連する単一 / 複合ユースケースを選び、オンデマンド取得で読む（手順は共通ルール『Wikiページのオンデマンド取得』）

エージェントが起票する Issue（ルール改修 Issue・不具合 Issue）は起票側で重複を抑止していないため、同じ内容が何度も上がる。
ラベルで引く 2 本目の検索は、キーワードが揃わなくても同種の報告を取りこぼさないために置いている。

### 重複の判定

調査で見つかった open の Issue / PR を 1 件ずつ対象 Issue と突き合わせ、次の 3 通りのどれかに判定する。

| 判定 | 条件 | 進む先 |
| --- | --- | --- |
| 重複なし | 同じ内容のものが 1 件も無い | 「作業単位への分解」へ進む（「既存の作業への統合」は実行しない） |
| 同じ内容 | 同じ内容で、対象 Issue にしかない情報が無い | 「既存の作業への統合」（転記なし） |
| 追加情報あり | 同じ内容だが、対象 Issue にしかない情報がある | 「既存の作業への統合」（転記あり） |

何をもって「同じ内容」とするかは対象 Issue の出所で変わる。

| 対象 Issue の出所 | 見分け方 | 同じ内容とみなす条件 |
| --- | --- | --- |
| ルール改修 Issue | `AI不具合報告` ラベルあり + 本文に `## 対象ルール` | 対象ルールのページが同じで、引用されている記述箇所も同じ |
| 不具合 Issue | `AI不具合報告` ラベルあり + 本文に `## 事象` | 該当ページが同じで、起きている事象も同じ |
| ユーザー起票の要望 | `AI不具合報告` ラベルなし | 同じ成果物を同じ目的で変更する |

対象範囲が重なるだけで目的が異なるもの（同じファイルを別の理由で触る等）は重複としない。
`## 報告元`（プロジェクト / エージェント / 対象番号）だけが違うものは同じ内容として扱う。
同じルール・同じ手順書の欠陥を別の場所で踏んだだけで、直す先は 1 箇所のため。

closed の Issue / PR は内容が一致していても統合先にしない（終わった作業へ転記しても誰も読まないため）。
同じ内容が closed になっているだけなら重複なしとして扱い、通常どおり分解判定へ進む。

### 既存の作業への統合

重複ありと判定した場合は、以降の手順を実行せず本節だけを行って自ターンを終える。
ユーザーへの確認は挟まない（重複と判定できた時点で統合先は一意に決まるため）。

判定が「追加情報あり」の場合、MCP `comment` を呼ぶ:
- `number`: 統合先の番号
- `is_pr`: 統合先が PR なら true
- `sender`: `intake-issue-triager`
- `format`:
  - `type`: `plain`
  - `body`: 対象 Issue にしかない内容の転記 + 出典（対象 Issue の番号）

統合先のラベル・assignee は変更しない（進行中の作業を止めないため）。

続いて対象 Issue へ MCP `comment` を呼ぶ:
- `number`: $issue_number
- `is_pr`: false
- `sender`: `intake-issue-triager`
- `format`:
  - `type`: `plain`
  - `body`: 統合先の番号と、統合した旨

続けて MCP `close` を呼ぶ:
- `number`: $issue_number
- `is_pr`: false
- `reason`: `not_planned`

続けて MCP `report_completion` を呼ぶ:
- `agent_name`: `intake-issue-triager`
- `number`: $issue_number

確認ラベルはモニターが close を検知した周期で除去する（個別解放）。

### 作業単位への分解

Issue の本文を読み、含まれる作業を独立したスコープごとに分解する。

- 依存関係 or 共通目的あり → 1 つの作業単位にまとめる
- 独立した機能 / 目的が混在 → 複数の作業単位に分割
- 迷ったら「同じ PR ツリーで進行するか」で判断

### 作業単位のラベル

作業単位は全て epic として扱う（判定フローチャート（レイヤー））。
シナリオへの影響判定は epic-conductor と story-conductor が担当するため、intake ではレイヤーを判定しない。

作業単位ごとに作る子 PR へ付与するラベル（値は環境変数を `echo` で解決する）:

| layer ラベル | 確認ラベル |
| --- | --- |
| `$AI_MONITOR_LABEL_LAYER_EPIC` の値 | `$AI_MONITOR_LABEL_CONFIRM_EPIC_CONDUCTOR` の値 |

### type / layer ラベルの付与

intake Issue には集約元を示す layer ラベルと、内容から判定した type ラベルを付ける。

type ラベルは以下から 1 つ判定する:

- 既存の動作が仕様または期待と異なる問題の修正: `$AI_MONITOR_LABEL_TYPE_BUG` の値
- 新機能追加・既存機能の有意な拡張: `$AI_MONITOR_LABEL_TYPE_FEAT` の値
- 外部動作を変えずにコードを整理・改善: `$AI_MONITOR_LABEL_TYPE_REFACTOR` の値
- ドキュメント・コメントのみの変更: `$AI_MONITOR_LABEL_TYPE_DOCS` の値
- ビルド設定・依存更新・CI/CD など: `$AI_MONITOR_LABEL_TYPE_CHORE` の値
- テストコードの追加・修正のみ: `$AI_MONITOR_LABEL_TYPE_TEST` の値

MCP `add_labels` を呼ぶ:
- `number`: $issue_number
- `is_pr`: false
- `labels`:
  - `$AI_MONITOR_LABEL_LAYER_INTAKE` の値
  - 判定した type ラベルの値

### 分解案の提示

判定結果を全件まとめてユーザーに提示する。

MCP `comment` を呼ぶ:
- `number`: $issue_number
- `is_pr`: false
- `sender`: `intake-issue-triager`
- `receiver`: ユーザーログイン名（`gh api user --jq '.login'` で取得）
- `format`:
  - `type`: `plain`
  - `body`:
    ```
    Issue の内容を以下の通り分解しました。

    | レイヤー | タイトル案 | 概要 |
    | --- | --- | --- |
    | epic | {タイトル案} | {概要} |

    - 問題なければ `議論中` ラベルを外す → 承認された案ごとにブランチと Draft PR を作成
    - 修正が必要なら assignee を外してフィードバックコメントを記入
    ```

### 確認質問の投稿

本当に判断が割れる、後戻りが大きい論点だけに絞る。
目安は 2〜3 件までとし、迷ったら質問数を減らす方向で判断する。
確認が必要な事項が無ければこの手順（`ask_questions` の呼び出し）を省略し、「議論中 付与 + 待機」に進む。

観点例に限らず、今回の Issue に確認が必要な事項を洗い出し、AI 側で推奨案を用意して投稿する。

下表は判断が分かれやすい観点の例で、毎回出す質問ではない。
本文・既存の設計書・上位 Issue から答えが一意に定まる観点は質問せず、前提として置いた判断を完了報告に書く。
質問する範囲は分解の仕方（作業単位の切り方・既存 Issue との関係）に限る。

| 観点 | 質問 | 選択肢例 |
| --- | --- | --- |
| 既存機能との関係 | 「既存の {類似機能} との扱いは？」 | 統合する / 別立てで併存 / 既存を廃止して置き換え |
| 依存 Issue の確認（調査でヒットした場合） | 「#{番号} が終わるまで着手できない依存がありそうです。理解は合っていますか？」 | 合っている / 無関係 / 補足あり（{内容}） |
| 分解した epic 間の順序（2 件以上に分解した場合） | 「{epic A} が終わってから {epic B} に着手する順序で合っていますか？」 | 合っている / 順序は不要（並行可） / 別の順序（{内容}） |
| バグ再現条件（type:bug 時） | 「再現手順・環境の理解は合っていますか？」 | 合っている / 追加条件がある（{条件}） |
| 上記以外 | 対象の内容から確認が要ると判断した論点 | その場で組み立てる |

MCP `ask_questions` を呼ぶ:
- `number`: $issue_number
- `is_pr`: false
- `sender`: `intake-issue-triager`
- `receiver`: ユーザーログイン名
- `questions`: 上記観点表から抽出

### 議論中 付与 + 待機

MCP `add_labels` を呼ぶ:
- `number`: $issue_number
- `is_pr`: false
- `labels`:
  - `$AI_MONITOR_LABEL_IN_DISCUSSION` の値

続けて MCP `set_assignee` を呼ぶ:
- `number`: $issue_number
- `is_pr`: false

### 作業完了報告

MCP `report_completion` を呼ぶ:
- `agent_name`: `intake-issue-triager`
- `number`: $issue_number
