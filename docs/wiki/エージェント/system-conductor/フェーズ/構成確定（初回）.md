# 構成確定（初回）

立ち上げ Issue から system ブランチ + Draft PR を作り、その本文の 概要 / 背景 / 構成要件 / エピック一覧 を草案として作成して確認事項を投稿し、待機に入る。
入力源は `リバースエンジニアリング` ラベルの有無で変わり、新規プロジェクトはユーザーの説明、既存プロジェクトの移行は system ブランチに入った現状のアーキテクチャ図と機能の洗い出しを読む。

## 手順

### ラベルの付与

MCP `add_labels` を呼ぶ:
- `number`: $number
- `is_pr`: false
- `labels`:
  - `$AI_MONITOR_LABEL_LAYER_SYSTEM` の値
  - 新規プロジェクトの場合は `$AI_MONITOR_LABEL_TYPE_FEAT` の値、既存プロジェクトの移行の場合は `$AI_MONITOR_LABEL_TYPE_DOCS` の値

### 入力源の読み取り

- `リバースエンジニアリング` ラベルがない場合、立ち上げ Issue の本文から実現したいことと制約を読む（実装コードは読まない）
- `リバースエンジニアリング` ラベルがある場合、system ブランチの `設計図/アーキテクチャ図.md` からサブシステム分割・言語・外部システムを読み、architecture-reverse-engineer の完了報告コメントから機能の洗い出しを読む（実装コードは読まない）

### system ブランチの作成

立ち上げ Issue の本文から決めたドメイン名で system ブランチを組み立てる。

`リバースエンジニアリング` ラベルがある場合、RE 起動で作成済みの system ブランチをそのまま使う（新しく切り直さない。「system ブランチの作成」は実行しない）。

MCP `worktree_create` を呼ぶ:
- `branch`: `docs/system/{ドメイン}/base`
- `base_ref`: `origin/master`

### system Draft PR の作成

MCP `create_draft_pr` を呼ぶ:
- `head_branch`: system ブランチ
- `base_branch`: `master`
- `title`: プロジェクト名
- `body`: `## 紐づく Issue`（`- #$number`）のみ
- `labels`:
  - `$AI_MONITOR_LABEL_LAYER_SYSTEM` の値
  - 立ち上げ Issue に付けたのと同じ `type:*` ラベルの値
  - `リバースエンジニアリング` ラベルがある場合はその値

### 監視面の登録

MCP `add_watch_targets` を呼ぶ:
- `agent_name`: `system-conductor`
- `number`: $number
- `watch_numbers`: 作成した PR の番号

### 確認ラベルの付け替え

以降のやり取りは system PR 上で行うため、手番を立ち上げ Issue から PR へ移す。

MCP `add_labels` を呼ぶ:
- `number`: 作成した PR の番号
- `is_pr`: true
- `labels`:
  - `$AI_MONITOR_LABEL_CONFIRM_SYSTEM_CONDUCTOR` の値

続けて MCP `remove_labels` を呼ぶ:
- `number`: $number
- `is_pr`: false
- `labels`:
  - `$AI_MONITOR_LABEL_CONFIRM_SYSTEM_CONDUCTOR` の値

### 構成要件の整理

満たすべき構成要件を リポジトリ / サブシステム / 言語 / 外部システム の 4 カテゴリで整理する。
各要件は銘柄ではなく満たすべき性質で書く（`認証は外部 IdP に委譲する` の形）。
銘柄が未定の外部システムは `{種別}（銘柄未定）` の形で記録する。
サブシステムには子 subsystem PR の `scope:*` ラベルに使う識別子を割り当てる。

### エピック一覧の作成

実現したいことを機能単位に分解し、`判定フローチャート/エピック分割.md` に沿って epic に束ねる（判定フローチャートのオンデマンド取得は共通ルール『Wikiページのオンデマンド取得』）。
epic ごとに所属ユースケースと着手順を決める。
共通基盤にあたる epic を参照元として特定し、着手順の先頭に置く。

### 本文の反映

PR 本文テンプレート「システム」の構成に沿って 概要 / 背景 / 構成要件 / エピック一覧 を作る（`対応 PR` 列は全行 `未作成`）。

MCP `update_body` を呼ぶ:
- `number`: 作成した PR の番号
- `is_pr`: true
- `body`: 草案を反映した本文

### 確認事項の投稿

確認したい論点を洗い出し、1 論点 = 1 コメントで投稿する。
対象は次の 2 種類で、特に 2 つ目（ユーザーが触れていない項目）を落とさない。

| 種類 | 内容 |
| --- | --- |
| 判断が割れる論点 | 複数の案が成立し、どれを採るかでプロジェクト全体の形が変わるもの |
| 入力に無い項目 | 構成要件の 4 カテゴリ（リポジトリ / サブシステム / 言語 / 外部システム）とエピック一覧のうち、ユーザーの説明に一度も出てこなかったもの |
| 上記以外 | 上の 2 種類に当てはまらないが、確認しておきたいと判断した論点 |

入力に無い項目は、4 カテゴリを 1 つずつ突き合わせて洗い出す。
ユーザーが技術構成に全く触れていない場合は、こちらが大半になる。
既存プロジェクトの移行では、実装と要件が乖離している箇所と epic の切り方も論点に含める。

いずれも仮置きの案を本文に書いたうえで、その根拠と他の選択肢をコメントで示す（質問だけを投げて本文を空欄にしない）。

論点 1 件ごとに MCP `comment` を呼ぶ:
- `number`: 作成した PR の番号
- `is_pr`: true
- `sender`: `system-conductor`
- `receiver`: ユーザーログイン名（`gh api user --jq '.login'` で取得）
- `format`:
  - `type`: `plain`
  - `body`: 論点 + 他に取り得た選択肢 + 推奨と理由

### 議論中 付与 + 待機

MCP `add_labels` を呼ぶ:
- `number`: 作成した PR の番号
- `is_pr`: true
- `labels`:
  - `$AI_MONITOR_LABEL_IN_DISCUSSION` の値

続けて MCP `set_assignee` を呼ぶ:
- `number`: 作成した PR の番号
- `is_pr`: true

### 作業完了報告

MCP `report_completion` を呼ぶ:
- `agent_name`: `system-conductor`
- `number`: $number
