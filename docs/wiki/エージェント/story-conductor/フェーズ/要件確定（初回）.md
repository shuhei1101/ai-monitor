# 要件確定（初回）

story PR 本文（概要 / 背景 / ユースケース要件）の草案を作成し、確認事項を投稿して待機に入る。

## 手順

### 親 epic の確認

MCP `get_issue_or_pr` を呼び、親 epic の内容を読む:
- `number`: 初期処理で取得した `parent` の番号
- `is_pr`: true
- `comments`: false

親 epic の `## ユースケース一覧` の UC 名と story PR のタイトルを照合し、自 story が担当する UC を特定する。あわせて `## 横断要件` を把握する。
特定した行の `変更種別` を見て、以降の現状調査の要否を決める（`新規` は調査なし、`変更` / `削除` は既存実装の現状を調べる）。

### 本文の作成

テンプレート（PR本文/ストーリーベース）に沿って 3 セクション（`## 概要` / `## 背景` / `## ユースケース要件`）の草案を作成する。

- `## 背景` に「親 epic #{番号} の UC「{UC 名}」に対応」の 1 行を必ず含める
- `## ユースケース要件` に epic 横断要件を参照する行がある場合、補足に「epic 横断要件「{要件の要旨}」に基づく」を明記する
- 単一ユースケースへの影響の判定結果（判定フローチャート（レイヤー）の ※3）を `## ユースケース要件` の直後に 1 行で書く。
  影響なしと判断した場合は `単一ユースケースへの影響: なし（{根拠}）` と明記する（後続ターンがこの記述で経路を決める）

MCP `update_body` を呼ぶ:
- `number`: $number
- `is_pr`: true
- `body`: 作成した本文

### 確認質問の投稿

以下の観点から今回の story に該当するものだけを抽出し、本文・親 epic の内容から AI 側で推奨案を判断して投稿する。
抽出結果が 0 件のときは `ask_questions` を呼ばずに次の手順へ進む。

下表は判断が分かれやすい観点の例で、毎回出す質問ではない。
本文・既存の設計書・上位 Issue から答えが一意に定まる観点は質問せず、前提として置いた判断を完了報告に書く。
質問する範囲は story レイヤーが決める論点（UC 要件（振る舞い・条件・境界））に限る。
既存の挙動を変える場合、その挙動を呼び出している側・参照している側の修正は当然に同じ story の範囲に含まれるので、スコープに含めるかは質問しない。
実装方法・関数シグネチャ・型・ライブラリ選定・ファイル構成は subsystem 以下の担当なので質問しない。

| 観点 | 質問 | 選択肢例 |
| --- | --- | --- |
| UC 粒度 | 「この story は 1 UC で表現できていますか？」 | 1 UC で表現できている / 複数 UC に分けたほうがよい（{分割案}） |
| 横断要件の適用 | 「epic 横断要件「{要件}」は本 UC でも適用しますか？」 | 適用する / 適用しない（{理由}） |
| 単一ユースケースへの影響 | 「`設計図/シナリオ/単一ユースケース/` の新規作成・更新を伴いますか？」 | 伴わない（実装だけの変更） / 伴う |
| 上記以外 | story レイヤーで決める論点のうち、判断が分かれるもの | その場で組み立てる |

MCP `ask_questions` を呼ぶ:
- `number`: $number
- `is_pr`: true
- `sender`: `story-conductor`
- `receiver`: ユーザーログイン名
- `questions`: 上記観点表から抽出

### 議論中 付与 + 待機

確認質問を 1 件も投稿しなかった場合は本手順を実行しない。
`確認:{自分}` を保持したまま自ターンを終え、次のターンで「要件確定（完了処理）」へ進む（判断が分かれる論点が無いのに手を止めない）。

MCP `add_labels` を呼ぶ:
- `number`: $number
- `is_pr`: true
- `labels`:
  - `$AI_MONITOR_LABEL_IN_DISCUSSION` の値

続けて MCP `set_assignee` を呼ぶ:
- `number`: $number
- `is_pr`: true

### 作業完了報告

MCP `report_completion` を呼ぶ:
- `agent_name`: `story-conductor`
- `number`: $number
