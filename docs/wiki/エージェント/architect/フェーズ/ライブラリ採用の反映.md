# ライブラリ採用の反映

ユーザーが決定した採用ライブラリを外部ライブラリ Wiki に反映し、内容の確認を依頼して待機する。

## 手順

### 外部ライブラリ Wiki の作成

subsystem ブランチの worktree へ移動し、`git pull --ff-only` でリモートの最新を取り込む。

`外部ライブラリ/{lib名}.md` を作成 / 更新し、`外部ライブラリ/README.md` の一覧に行を追加して commit push する。
記入内容は PoC PR 本文の `## 検証対象` / `## 調査結果`（PoC を実施していない場合は library-researcher の調査結果）から転記する。

- 一覧の使用箇所列には、そのライブラリを呼び出す境界層のパス（設計で決めたラッパーの置き場）を書く
- 既存ライブラリの使用箇所が今回の設計で変わる場合は、その行の使用箇所列も同じ commit で更新する

### 非機能要件への反映

採用したライブラリの制約（レートリミット・上限値・ライセンス・対応バージョン 等）のうち、アプリ全体の値を決める必要があるものを `設計図/非機能要件.md` の `## 一覧` に追記して commit push する（書式はテンプレート「非機能要件」のオンデマンド取得。共通ルール『Wikiページのオンデマンド取得』）。

- 外部の制約列にライブラリ側の値、出所列に `外部ライブラリ/{lib名}.md` へのリンク、アプリの決定値列と根拠列に今回決めた値とその理由を書く
- 追加した行ごとに詳細セクション（`## {項目名}`）も作る（超過時の挙動 / 内訳 / 非機能要件テスト）
- 決められない項目も同じ表に行を作り、決定値列を `未確定`・根拠列に決める条件を書く
- アプリ全体に効く値なので、追記した行は必ず「確認事項の投稿」でユーザーに確認する（subsystem の判断だけで確定させない）
- 制約がアプリの値に影響しない場合は本手順を実行しない

### 確認事項の投稿

確認したい論点を洗い出し、1 論点 = 1 コメントで投稿する。
投稿先は論点がページの特定箇所に紐づくかで分ける。

採用理由や使い方など記述に紐づく論点は、1 件ごとに MCP `create_review_comment` を呼ぶ:
- `pr_number`: $pr_number
- `path`: `外部ライブラリ/{lib名}.md` のパス
- `line`: 論点にあたる行
- `sender`: `architect`
- `receiver`: ユーザーログイン名（`gh api user --jq '.login'` で取得）
- `body`: その行で選んだ内容 + 他に取り得た選択肢 + 推奨（いま書いてある案）と理由

ページに紐づかない論点（他ライブラリとの併用方針・導入範囲 等）は、1 件ごとに MCP `comment` を呼ぶ:
- `number`: $pr_number
- `is_pr`: true
- `sender`: `architect`
- `receiver`: ユーザーログイン名
- `format`:
  - `type`: `plain`
  - `body`: 論点 + 他に取り得た選択肢 + 推奨と理由

### 補足事項の投稿

commit した内容を読み返し、共通ルール『インラインコメント』に沿って補足事項を該当行へ投稿する。

### 反映報告の投稿 + 待機

MCP `comment` を呼ぶ:
- `number`: $pr_number
- `is_pr`: true
- `sender`: `architect`
- `receiver`: ユーザーログイン名
- `format`:
  - `type`: `plain`
  - `body`: Wiki 反映の報告（作成 / 更新したページ名 + 記載内容の要約 + 投稿した確認事項の件数 + 承認・修正方法の案内）

続けて MCP `add_labels` を呼ぶ:
- `number`: $pr_number
- `is_pr`: true
- `labels`:
  - `$AI_MONITOR_LABEL_IN_DISCUSSION` の値

続けて MCP `set_assignee` を呼ぶ:
- `number`: $pr_number
- `is_pr`: true

### 作業完了報告

MCP `report_completion` を呼ぶ:
- `agent_name`: `architect`
- `number`: $pr_number
