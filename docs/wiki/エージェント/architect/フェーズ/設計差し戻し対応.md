# 設計差し戻し対応

worker が設計 Wiki どおりに進められないと報告してきた箇所を修正し、ユーザーに確認を依頼して待機する。

## 手順

### 差し戻し内容の確認と設計 Wiki の修正

差し戻し報告コメントから、設計 Wiki のどの記述が実現できないかと理由を読む。
subsystem ブランチの worktree へ移動し、`git pull --ff-only` でリモートの最新を取り込む。

該当ページを修正して commit push する。

`チェックシート/設計変更影響調査.md` で、修正が上流 → 下流の全レイヤーに行き渡っているかを確認する。

- subsystem レイヤーで解決できない論点（要件の矛盾・外部制約による方針転換）の場合、本フェーズでは修正せず「エスカレーション報告」の手順を実行する（以降の手順は実行しない）

### 確認事項の投稿

修正のうち判断が割れるもの（別の直し方も取り得たもの）を洗い出し、1 論点 = 1 コメントで投稿する。
投稿先は論点がページの特定箇所に紐づくかで分ける。

ページの特定箇所に紐づく論点は、1 件ごとに MCP `create_review_comment` を呼ぶ:
- `pr_number`: $pr_number
- `path`: 修正した設計ページのパス
- `line`: 修正箇所の行
- `sender`: `architect`
- `receiver`: ユーザーログイン名（`gh api user --jq '.login'` で取得）
- `body`: その行をどう直したか + 他に取り得た直し方 + 推奨（いま書いてある案）と理由

ページに紐づかない論点（修正の波及範囲・他ページとの整合 等）は、1 件ごとに MCP `comment` を呼ぶ:
- `number`: $pr_number
- `is_pr`: true
- `sender`: `architect`
- `receiver`: ユーザーログイン名
- `format`:
  - `type`: `plain`
  - `body`: 論点 + 他に取り得た選択肢 + 推奨と理由

### 修正内容の返信 + 待機

MCP `reply_comment` を呼ぶ:
- `comment_node_id`: 差し戻し報告コメントの node_id
- `sender`: `architect`
- `receiver`: ユーザーログイン名
- `format`:
  - `type`: `plain`
  - `body`: 修正内容（修正した設計ページ名 + 修正 commit の ID + 投稿した確認事項の件数）と確認依頼

続けて MCP `add_labels` を呼ぶ:
- `number`: $pr_number
- `is_pr`: true
- `labels`:
  - `$AI_MONITOR_LABEL_IN_DISCUSSION` の値

続けて MCP `set_assignee` を呼ぶ:
- `number`: $pr_number
- `is_pr`: true

`確認:architect` は除去しない（承認後の再開指示で復帰するため）。

### 作業完了報告

MCP `report_completion` を呼ぶ:
- `agent_name`: `architect`
- `number`: $pr_number
