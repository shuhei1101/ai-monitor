# 応答ループ

待機中のユーザーフィードバックに対応し、再び待機に入る。
どの待機かは、未応答のユーザー発言が付いた自分宛スレッドの文脈で判断する。
ユーザーとの会話面は subsystem PR のみ（PoC PR 側は発注元とのやり取りだけ）。

## 手順

### 内容に応じた対応

| 待機の文脈 | 対応 |
| --- | --- |
| 設計提案への修正指示 | 対象ページを修正して commit push し、「本ページの {箇所} を更新しました」と短く追記 |
| 設計提案の議論中に生じたライブラリ選定論点 | 「SS設計（初回）」の「ライブラリ候補の提示」を実行する |
| 候補・検証観点への修正指示 | 候補の追加調査 / 検証観点の見直しを行い、更新後の候補比較を追記 |
| 結果まとめへの質問 | PoC PR 本文の記録を根拠に回答を追記 |
| 結果まとめへの追加検証の依頼 | 該当 PoC PR に追加の検証観点を書いた再検証指示コメント（`receiver`: `library-poc-runner`）を投稿してから `$AI_MONITOR_LABEL_CONFIRM_LIBRARY_POC_RUNNER` を再付与し、依頼を受け付けた旨を追記 |
| 外部ライブラリ Wiki への修正指示 | `外部ライブラリ/{lib名}.md` を修正して commit push し、短く追記 |
| 適合候補なしの相談への方針指示 | 指示された方針（自作 / 要件緩和 / 設計変更）で候補調査をやり直し、結果を追記 |
| 設計差し戻しの修正内容への修正指示 | 設計 Wiki を修正して commit push し、修正 commit の ID を追記 |
| 上記以外 | 文脈から必要な対応を判断して実施し、対応内容を短く追記 |

追記は MCP `reply_comment` を呼ぶ:
- `comment_node_id`: 返信対象コメントの node_id
- `sender`: `architect`
- `receiver`: ユーザーログイン名（`gh api user --jq '.login'` で取得）
- `format`:
  - `type`: `plain`
  - `body`: 返信本文

### assignee 再設定

MCP `set_assignee` を呼ぶ:
- `number`: $pr_number
- `is_pr`: true

### 作業完了報告

MCP `report_completion` を呼ぶ:
- `agent_name`: `architect`
- `number`: $pr_number
