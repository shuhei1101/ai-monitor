# 実装レビュー

implementer の diff を自分が確定させた設計 Wiki と照合し、テストを実行して Green を確認したうえで Ready 化し、subsystem-conductor に一式完了を報告する。
ユーザーとのやり取りはせず、設計 Wiki との差異も fail も担当の worker に差し戻す。
自分が修正するのは設計 Wiki だけで、実装コード・テストコードには触れない。

## 手順

### diff のレビュー

完了報告のコミット表から見る範囲を決め、差分を取得する（共通ルール『PR差分の取得』）。
取得した差分を設計 Wiki（ER図 / 画面構成 / 結合 / モジュール構成）と一対一で突き合わせて確認し、バグ・可読性・保守性を見る。

- diff に指摘がある場合、「インライン指摘の投稿」へ進む
- 指摘がない場合、「テストの実行」へ進む（「インライン指摘の投稿」は実行しない）

### インライン指摘の投稿

指摘 1 件ごとに MCP `create_review_comment` を呼ぶ:
- `pr_number`: $pr_number
- `path`: 指摘対象のファイルパス
- `line`: 指摘対象の行
- `sender`: `architect`
- `receiver`: `implementer`
- `body`: 設計 Wiki との差異・バグ・可読性の問題と期待する修正

続けて MCP `reply_comment` を呼ぶ:
- `comment_node_id`: implementer の完了報告コメントの node_id
- `sender`: `architect`
- `receiver`: `implementer`
- `format`:
  - `type`: `plain`
  - `body`: インライン指摘への対応依頼（指摘の件数と要点。スレッドは Resolve しない）

続けて MCP `transition_phase` を呼ぶ:
- `number`: $pr_number
- `is_pr`: true
- `remove_labels_`:
  - `$AI_MONITOR_LABEL_CONFIRM_ARCHITECT` の値
- `add_labels_`:
  - `$AI_MONITOR_LABEL_CONFIRM_IMPLEMENTER` の値

「作業完了報告」を実行して自ターンを終える（以降の手順は実行しない）。

### テストの実行

成果物ブランチの worktree へ移動し、`git pull --ff-only` でリモートの最新を取り込む。

`## 単体テスト結果` / `## 結合テスト結果` / `## 単一ユースケースシナリオテスト結果` / `## 複合ユースケースシナリオテスト結果` に載っているテストを実行して Green を実測する。

### テスト結果表の記入

テスト結果表の結果列を実行結果で埋める（`✅` / `❌`）。

MCP `update_body` を呼ぶ:
- `number`: $pr_number
- `is_pr`: true
- `body`: 更新後本文

分岐:

- 全て Green の場合、「Draft 解除」へ進む
- `❌` がある場合、「fail のトリアージ」へ進む（「Draft 解除」以降は実行しない）

### fail のトリアージ

失敗したケースの内容を設計 Wiki・実装コード・テストコードと照合し、原因を判定する
実装コード・テストコードの修正は行わず、担当の worker に差し戻す（実装の依存関係を把握しているのは worker 側のため）。

| 判定 | 根拠 | 対応 |
| --- | --- | --- |
| 実装側の問題 | 設計 Wiki もテストコードも正しく、実装が期待する振る舞いを満たしていない | 「実装側の問題の差し戻し」へ進む |
| 設計側の問題 | 設計 Wiki の記述が実装すべき要件と矛盾している | 「設計側の問題の修正」へ進む |
| テストコード側の問題 | 設計 Wiki も実装も正しく、テストコードが誤っている | 「テストコード側の問題の差し戻し」へ進む |
| 上記以外 | 3 つのどれとも判定できない | subsystem-conductor へエスカレーション報告して判断を仰ぐ（「エスカレーション報告」フェーズ） |

### 実装側の問題の差し戻し

fail 箇所 1 件ごとに MCP `create_review_comment` を呼ぶ:
- `pr_number`: $pr_number
- `path`: fail の原因になっている実装のファイルパス
- `line`: 対象の行
- `sender`: `architect`
- `receiver`: `implementer`
- `body`: fail の内容（テスト名 + 失敗メッセージ）と設計 Wiki が期待する振る舞い

続けて MCP `reply_comment` を呼ぶ:
- `comment_node_id`: implementer の完了報告コメントの node_id
- `sender`: `architect`
- `receiver`: `implementer`
- `format`:
  - `type`: `plain`
  - `body`: fail 内容の要約と再修正の依頼（スレッドは Resolve しない）

続けて MCP `transition_phase` を呼ぶ:
- `number`: $pr_number
- `is_pr`: true
- `remove_labels_`:
  - `$AI_MONITOR_LABEL_CONFIRM_ARCHITECT` の値
- `add_labels_`:
  - `$AI_MONITOR_LABEL_CONFIRM_IMPLEMENTER` の値

「作業完了報告」を実行して自ターンを終える（以降の手順は実行しない）。

### 設計側の問題の修正

設計 Wiki を修正して commit push する（実装コードには触れない）。

MCP `reply_comment` を呼ぶ:
- `comment_node_id`: implementer の完了報告コメントの node_id
- `sender`: `architect`
- `receiver`: `implementer`
- `format`:
  - `type`: `plain`
  - `body`: 設計 Wiki の修正内容（修正したページ名 + 修正 commit の ID）と、修正後の設計に合わせた再実装の依頼（スレッドは Resolve しない）

続けて MCP `transition_phase` を呼ぶ:
- `number`: $pr_number
- `is_pr`: true
- `remove_labels_`:
  - `$AI_MONITOR_LABEL_CONFIRM_ARCHITECT` の値
- `add_labels_`:
  - `$AI_MONITOR_LABEL_CONFIRM_IMPLEMENTER` の値

「作業完了報告」を実行して自ターンを終える（以降の手順は実行しない）。

### テストコード側の問題の差し戻し

MCP `reply_comment` を呼ぶ:
- `comment_node_id`: implementer の完了報告コメントの node_id
- `sender`: `architect`
- `receiver`: `implementer`
- `format`:
  - `type`: `plain`
  - `body`: トリアージ結果（テストコード側の問題と判定した根拠・実装は設計どおりである旨）

続けて MCP `resolve_comments` を呼ぶ:
- `node_ids`: implementer の完了報告コメントの `node_id`

続けて MCP `comment` を呼ぶ:
- `number`: $pr_number
- `is_pr`: true
- `sender`: `architect`
- `receiver`: `tester`
- `format`:
  - `type`: `plain`
  - `body`: テストコードの誤りの指摘（テスト名 + 失敗メッセージ + 設計 Wiki が期待する値）と修正の依頼

続けて MCP `transition_phase` を呼ぶ:
- `number`: $pr_number
- `is_pr`: true
- `remove_labels_`:
  - `$AI_MONITOR_LABEL_CONFIRM_ARCHITECT` の値
- `add_labels_`:
  - `$AI_MONITOR_LABEL_CONFIRM_TESTER` の値

「作業完了報告」を実行して自ターンを終える（以降の手順は実行しない）。

### Draft 解除

MCP `mark_pr_ready` を呼ぶ:
- `pr_number`: $pr_number

### レビュー結果の返信と Resolve

MCP `reply_comment` を呼ぶ:
- `comment_node_id`: implementer の完了報告コメントの node_id
- `sender`: `architect`
- `receiver`: `implementer`
- `format`:
  - `type`: `plain`
  - `body`: レビュー結果（テスト実行の実測結果 + 指摘なし）

続けて MCP `resolve_comments` を呼ぶ:
- `node_ids`: implementer の完了報告コメントの `node_id`

### インライン指摘スレッドの解決

MCP `list_review_threads` を呼ぶ:
- `pr_number`: $pr_number
- `addressee`: `architect`
- `include_resolved`: false

続けて MCP `resolve_review_threads` を呼ぶ:
- `thread_node_ids`: 取得したスレッドの `node_id` 配列

### タスク一覧のチェックと確認

成果物 PR 本文の `## タスク一覧` のテスト実行タスクを `[x]` にする（テストを実行したのは自分）。

MCP `update_body` を呼ぶ:
- `number`: $pr_number
- `is_pr`: true
- `body`: 更新後本文

続けて、設計・テスト作成・実装の各タスクが担当者によってチェック済みかを確認する（本手順の後に全行がチェック済みになる）。
チェックを入れるのは作業した本人なので、他人の行は自分では入れない。

- 未チェックのまま残っている行がある場合、その担当への完了報告コメントに追記して指摘し、チェックを入れてもらう

### subsystem-conductor への一式完了報告

MCP `comment` を呼ぶ:
- `number`: $pr_number
- `is_pr`: true
- `sender`: `architect`
- `receiver`: `subsystem-conductor`
- `format`:
  - `type`: `commits`
  - `body`: 一式完了報告（設計 → テスト → 実装 → レビューの結果要約 + テスト実測結果 + 差し戻しが発生した場合はその経緯）
  - `entries`: 積んだ commit の `commit` と `summary` の組

続けて MCP `add_labels` を呼ぶ:
- `number`: $pr_number
- `is_pr`: true
- `labels`:
  - `$AI_MONITOR_LABEL_CONFIRM_SUBSYSTEM_CONDUCTOR` の値

### ラベル除去

MCP `transition_phase` を呼ぶ:
- `number`: $pr_number
- `is_pr`: true
- `remove_labels_`:
  - `$AI_MONITOR_LABEL_CONFIRM_ARCHITECT` の値
- `add_labels_`: なし

### 作業完了報告

MCP `report_completion` を呼ぶ:
- `agent_name`: `architect`
- `number`: $pr_number
