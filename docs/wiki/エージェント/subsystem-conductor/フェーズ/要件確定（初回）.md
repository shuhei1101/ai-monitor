# 要件確定（初回）

subsystem PR 本文（概要 / 背景 / 現状 / システム要件（SA））の草案を作成し、確認事項を投稿して待機に入る。

## 手順

### 親 story の確認

MCP `get_issue_or_pr` を呼び、親 story の内容を読む:
- `number`: 初期処理で取得した `parent` の番号
- `is_pr`: true
- `comments`: false
- `sub_issues`: true

親 story の `## ユースケース要件` と自 Issue の `scope:*` ラベルを照合し、自 subsystem が担当する範囲を特定する。
親 story ブランチに commit 済みの単一 UC シナリオも読み、自 subsystem が実現するフローを把握する（シナリオの participant のうち自分の `scope:*` に対応するものが担当範囲、他の participant は兄弟 subsystem の担当）。

### 現状調査

`## 現状` の 2 表（関連 Issue/PR / 関連ドキュメント）の材料を集める。
判断材料は親 story と設計 Wiki に閉じ、実装コード・テストコードは読まない（実装の調査は architect の SS設計 が担う）。

- 関連 Issue / PR: サブエージェント `ai-monitor:related-issue-finder` と `ai-monitor:related-pr-finder` を並列起動し、戻り値（番号 / 状況 / 概要 / 関連性）をそのまま `### 関連 Issue/PR` の表に整形する（入力: $number と本文から抽出したキーワード）
- 関連ドキュメント: 注入済みの Wiki 索引を起点に、担当範囲に関係する設計 Wiki を洗い出す（オンデマンド取得は共通ルール『Wikiページのオンデマンド取得』）

`## 現状` の追加サブセクション:
- 親 story が `type:bug` の場合、親 story の記述から `### 再現手順` に期待と実際を転記する

### 本文の作成

テンプレート（イシュー本文/サブシステム）に沿って各セクションの草案を作成する。

- `## 背景` に「親 story #{番号} の {対象システム} 担当」の 1 行を必ず含める
- `## システム要件（SA）` は自 subsystem の担当範囲だけを書き、兄弟 subsystem の範囲は `### スコープ外` に回す
- 親 story の `sub_issues` に自分以外の subsystem がいる場合、着手順の想定を `## 背景` に 1 行書く（依存は張らない。story 配下は直列で進むため）

MCP `update_body` を呼ぶ:
- `number`: $number
- `is_pr`: true
- `body`: 作成した本文

### 親 story ブランチの特定

MCP `search_issues_and_prs` で親 story PR 番号を本文に含む open PR を特定する。

続けて MCP `get_issue_or_pr` を呼ぶ:
- `number`: 特定した story PR の番号
- `is_pr`: true
- `comments`: false

戻り値の `head_ref` が親 story ブランチ名。

### Draft PR の作成

親 story の type ラベル + 親 story ブランチ名 `{type}/story/{ドメイン}/{UC名}` から取り出したドメイン部と UC 名 + 本 subsystem の `scope:*` と変更内容から subsystem ブランチを組み立てる。

MCP `worktree_create` を呼ぶ:
- `branch`: `{type}/{scope}/{ドメイン}/{UC名}/{変更内容}`
- `base_ref`: `origin/{親 story ブランチ}`

続けて MCP `create_draft_pr` を呼ぶ:
- `head_branch`: 作成したブランチ
- `base_branch`: 親 story ブランチ
- `title`: subsystem のタイトル
- `body`: `## 紐づく Issue`（`- #$number`）と `## タスク一覧`
- `labels`: `$AI_MONITOR_LABEL_LAYER_SUBSYSTEM` の値

`## タスク一覧` は SA と現状調査の `### 関連ドキュメント` から、設計 Wiki の修正・実装・テスト実行の To Do をチェックボックスで列挙する（テンプレート「PR本文/サブシステム」の記述例に準拠）。

### 監視面の登録

MCP `add_watch_targets` を呼ぶ:
- `agent_name`: `subsystem-conductor`
- `number`: $number
- `watch_numbers`: 作成した PR の番号

### 完了報告の投稿

MCP `comment` を呼ぶ:
- `number`: $number
- `is_pr`: true
- `sender`: `subsystem-conductor`
- `receiver`: ユーザーログイン名（`gh api user --jq '.login'` で取得）
- `format`:
  - `type`: `plain`
  - `body`: SA とタスク一覧をまとめた確認依頼（要件の要点 + タスクの過不足の確認ポイント + 作成した PR へのリンク + 承認・修正方法の案内）

SA とタスク一覧は 1 回の確認にまとめる。
タスク一覧は SA から機械的に導ける内容なので、別々に承認を取ってもユーザーが見る材料は変わらない。


### 確認質問の投稿

以下の観点から今回の subsystem に該当するものだけを抽出し、本文・親 story の内容から AI 側で推奨案を判断して投稿する。
抽出結果が 0 件のときは `ask_questions` を呼ばずに次の手順へ進む。

下表は判断が分かれやすい観点の例で、毎回出す質問ではない。
本文・既存の設計書・上位 Issue から答えが一意に定まる観点は質問せず、前提として置いた判断を完了報告に書く。
質問する範囲は subsystem レイヤーが決める論点（サブシステムの担当範囲・外部との境界）に限る。
設計の中身（クラス分割・関数シグネチャ）は architect の担当なので質問しない。

| 観点 | 質問 | 選択肢例 |
| --- | --- | --- |
| 担当範囲の境界 | 「{境界にある機能} は本 subsystem と兄弟 subsystem のどちらで実装しますか？」 | 本 subsystem / 兄弟 subsystem（{番号}） |
| 既存機能の扱い | 「既存の {機能} は拡張しますか、新規に作りますか？」 | 既存を拡張 / 新規作成して既存は残す / 置き換える |
| バリデーション方針 | 「{入力} の検証はどこまで本 subsystem で持ちますか？」 | 本 subsystem で完結 / 兄弟 subsystem と二重に持つ |
| 非機能要件の基準値 | 「{性能 / セキュリティ} の基準値は {推奨値} でよいですか？」 | 推奨値でよい / 別の値（{値}） |
| スコープ外の確認 | 「{周辺機能} は今回スコープ外という理解で合っていますか？」 | 合っている / 含める |
| 上記以外 | subsystem レイヤーで決める論点のうち、判断が分かれるもの | その場で組み立てる |

MCP `ask_questions` を呼ぶ:
- `number`: $number
- `is_pr`: true
- `sender`: `subsystem-conductor`
- `receiver`: ユーザーログイン名
- `questions`: 上記観点表から抽出

### 議論中 付与 + 待機

確認質問を 1 件も投稿しなかった場合は本手順を実行しない。
`確認:subsystem-conductor` を保持したまま自ターンを終え、次のターンで「要件確定（完了処理）」へ進む。

MCP `add_labels` を呼ぶ:
- `number`: $number
- `is_pr`: true
- `labels`:
  - `$AI_MONITOR_LABEL_IN_DISCUSSION` の値

続けて MCP `set_assignee` を呼ぶ:
- `number`: $number
- `is_pr`: true

### 作業完了報告

MCP `report_completion` を呼ぶ:
- `agent_name`: `subsystem-conductor`
- `number`: $number
