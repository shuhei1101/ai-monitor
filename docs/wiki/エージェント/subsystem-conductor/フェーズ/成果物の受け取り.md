# 成果物の受け取り

配下が完成させた成果物 PR を subsystem ブランチへマージし、次の成果物ブランチ + Draft PR を切って次の担当へ渡す。

成果物ブランチが担当ごとに分かれるため、worker 同士は直接引き継がず必ず本フェーズを経由する（`プロジェクト管理/エージェント組織図.md`）。

## 手順

### 段階の判定

完了報告が投稿された成果物 PR の `head_ref` から、今どの段階かを判定する。

| 受け取った成果物ブランチ | 次に切るブランチ | 次の担当 | 次の PR の type ラベル |
| --- | --- | --- | --- |
| `docs/{scope}/{ドメイン}/{UC名}/interface` | `docs/{scope}/{ドメイン}/{UC名}/module` | architect | `$AI_MONITOR_LABEL_TYPE_DOCS` |
| `docs/{scope}/{ドメイン}/{UC名}/module` | `test/{scope}/{ドメイン}/{UC名}/{変更内容}` | tester | `$AI_MONITOR_LABEL_TYPE_TEST` |
| `test/{scope}/{ドメイン}/{UC名}/{変更内容}` | `{type}/{scope}/{ドメイン}/{UC名}/{変更内容}` | implementer | subsystem PR の `type:*` と同じ値 |
| 実装（`{type}` が subsystem PR の `type:*` と同じで、末尾がテストと同じ `{変更内容}`） | 切らない | 自分 | - |

`{変更内容}` は subsystem PR の `## タスク一覧` のテスト / 実装タスクから決め、テストと実装で同じ値を使う。

差し戻し由来の修正用 PR（`fix/{scope}/{ドメイン}/{UC名}/{変更内容}`）は本フェーズの対象外。
base が自分の subsystem ブランチではなく統合テストを実行しているブランチなので、マージは「マージ起動」→「subsystemマージ」の経路で行う。

### 完了報告の Resolve

MCP `resolve_comments` を呼ぶ:
- `node_ids`: 受け取った完了報告コメントの `node_id`

### 成果物 PR のマージ

`規約/マージ手順.md` に沿って base（自分の subsystem ブランチ）を取り込み、コンフリクトがないことを確認する。

- コンフリクトが発生した場合、成果物 PR に競合ファイルとどちらを残すかの相談コメントを投稿し、`議論中` 付与 + `assignee=ユーザー` で待機する（解消の往復は「応答ループ」で回し、全競合解消後に本手順へ合流する）

MCP `mark_pr_ready` を呼ぶ:
- `pr_number`: 成果物 PR の番号

続けて MCP `merge_pr` を呼ぶ:
- `pr_number`: 成果物 PR の番号
- `strategy`: `squash`

続けて MCP `worktree_remove` を呼ぶ:
- `branch`: 成果物ブランチ

続けて MCP `remove_watch_targets` を呼ぶ:
- `agent_name`: `subsystem-conductor`
- `number`: $number
- `watch_numbers`: マージした成果物 PR の番号

### 次の成果物 Draft PR の作成

実装を受け取った場合は本手順を実行しない（「次の担当への割り当て」も実行せず、「手番の置き場所」へ進む）。

MCP `worktree_create` を呼ぶ:
- `branch`: 上表の「次に切るブランチ」
- `base_ref`: `origin/{自分の subsystem ブランチ}`

続けて MCP `create_draft_pr` を呼ぶ:
- `head_branch`: 作成したブランチ
- `base_branch`: 自分の subsystem ブランチ
- `title`: `{subsystem のタイトル}（{成果物名}）`
- `body`: `## 紐づく Issue`（subsystem PR と同じ起点の Issue 番号）と `## タスク一覧`
- `labels`: 上表の type ラベルの値

`## タスク一覧` はその成果物の To Do をチェックボックスで列挙する（書式はテンプレート「PR本文/成果物」。テストは「PR本文/単体・結合テスト」）。
並べる行は subsystem PR の `## システム要件（SA）` から起こし、全行を未チェックで作る。

| 成果物 | 並べる行 |
| --- | --- |
| モジュール構成 | 作成 / 更新するモジュール構成のページ |
| 単体・結合テスト | 作成する単体テスト / 結合テストのファイル |
| 実装 | 実装する関数 / エンドポイントと、追随させるモジュール構成のページ |

続けて MCP `add_watch_targets` を呼ぶ:
- `agent_name`: `subsystem-conductor`
- `number`: $number
- `watch_numbers`: 作成した PR の番号

### 次の担当への割り当て

MCP `comment` を呼ぶ:
- `number`: 作成した PR の番号
- `is_pr`: true
- `sender`: `subsystem-conductor`
- `receiver`: 上表の「次の担当」
- `format`:
  - `type`: `pages`
  - `body`: 作業の指示（根拠になる設計 Wiki のページ名と、直前の成果物で確定した内容の要約）
  - `entries`: 各ページの `page` と `commit`（範囲があれば `start_commit` も）の組

続けて MCP `add_labels` を呼ぶ:
- `number`: 作成した PR の番号
- `is_pr`: true
- `labels`:
  - 上表の「次の担当」の確認ラベルの値

### 手番の置き場所

マージ済みの成果物 PR に付いていた `確認:subsystem-conductor` は merged で polling の対象から外れるため、ここでは触らない。

実装を受け取った場合だけ、手番を自 subsystem PR へ戻して「マージ起動」に続ける。

MCP `transition_phase` を呼ぶ:
- `number`: $number
- `is_pr`: true
- `remove_labels_`: なし
- `add_labels_`:
  - `$AI_MONITOR_LABEL_CONFIRM_SUBSYSTEM_CONDUCTOR` の値

### 作業完了報告

MCP `report_completion` を呼ぶ:
- `agent_name`: `subsystem-conductor`
- `number`: $number
