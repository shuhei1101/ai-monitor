# エスカレーション対応（方針確認）

architect から上がった論点に対して、subsystem レイヤーで打てる手と上位への中継を選択肢にしてユーザーに確認する。

## 手順

### 論点の整理と解決案の検討

エスカレーション報告コメントから論点と経緯を読む。
そのうえで、subsystem レイヤー（設計方針の変更・実装手段の代替など、自 subsystem に閉じた範囲）で打てる手があるかを検討する。

素通しはしない。
打てる手が思いつかない場合も、その理由を添えて選択肢に「上位への中継」だけを残す形で提示する。

### 対応方針案の投稿

操作対象は subsystem PR ではなく、エスカレーション報告を受け取った面（設計中は architect の成果物 PR）にする。
確認ラベルが付いている面と別の面へ置くと手番が 2 面に割れ、次フェーズが起動しなくなる（規約『フェーズ索引の網羅』の 1 面 1 確認ラベル）。

MCP `comment` を呼ぶ:
- `number`: エスカレーション報告を受け取った面の番号
- `is_pr`: true
- `sender`: `subsystem-conductor`
- `receiver`: ユーザーログイン名（`gh api user --jq '.login'` で取得）
- `format`:
  - `type`: `plain`
  - `body`:
    ```
    {論点の要約} について、subsystem レベルでの対応方針案です。

    | 案 | 内容 | 想定影響 |
    | --- | --- | --- |
    | A | {subsystem レベルの解決案} | {影響範囲} |
    | B | 親 story へエスカレーションする | {subsystem では解決できない理由} |

    推奨: {A / B}（{理由}）

    - 方針が決まったら記号で返信 + `議論中` ラベルを外す → その方針で進めます
    - 調整が必要なら assignee を外してフィードバックコメントを記入
    ```

### 議論中 付与 + 待機

MCP `add_labels` を呼ぶ:
- `number`: エスカレーション報告を受け取った面の番号
- `is_pr`: true
- `labels`:
  - `$AI_MONITOR_LABEL_IN_DISCUSSION` の値

続けて MCP `set_assignee` を呼ぶ:
- `number`: エスカレーション報告を受け取った面の番号
- `is_pr`: true

`確認:subsystem-conductor` は除去しない（選択後の実行で復帰するため）。

### 作業完了報告

MCP `report_completion` を呼ぶ:
- `agent_name`: `subsystem-conductor`
- `number`: エスカレーション報告を受け取った面の番号
