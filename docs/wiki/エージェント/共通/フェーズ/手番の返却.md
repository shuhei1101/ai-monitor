# 手番の返却

確認ラベルは付いているが手番の中身が無いまま起こされたとき、確認ラベルを外して手番を返す。

## 手順

### 起動要因の判定

初期処理で取得した本文・ラベル・コメント（Resolve 済みを含む）から、確認ラベルが付いた理由を次のどれかに切り分ける。

| 種類 | 見分け方 | 対応 |
| --- | --- | --- |
| 処理済みの再起動 | 直前の工程の成果物・コメントが揃っており、次の担当の確認ラベルも付いている | 「ラベル除去」へ進む |
| 手順書の穴 | 直前の工程は終わっているのに、次に進むフェーズが索引に無い | 「不具合の報告」へ進む |
| 進行が止まっている | 直前の工程の成果物が無く、誰も次を持っていない | 「不具合の報告」→「中断の報告」へ進む |

### 不具合の報告

共通ルール『不具合の報告』に沿って MCP `create_defect_issue` を呼ぶ:
- `source_pages`: 自分のフェーズ索引（`エージェント/{自分}/README.md`）と、直前に動いたフェーズのページ
- `body`: 確認ラベルが付いた状態で起動したが該当するフェーズが無かった経緯（対象の番号・付いていたラベル・直前の工程）
- `workaround`: 確認ラベルを外して手番を返した旨（進行が止まっている場合は省略する）

### 中断の報告

進行が止まっている場合だけ実行する。

MCP `comment` を呼ぶ:
- `number`: 起動要因になった対象の番号
- `is_pr`: 対象が PR なら true
- `sender`: `{自分}`
- `receiver`: ユーザーログイン名（`gh api user --jq '.login'` で取得）
- `format`:
  - `type`: `plain`
  - `body`: 進行が止まっている旨と起票した不具合 Issue へのリンク

続けて MCP `add_labels` を呼ぶ:
- `number`: 起動要因になった対象の番号
- `is_pr`: 対象が PR なら true
- `labels`: `$AI_MONITOR_LABEL_IN_DISCUSSION` の値

続けて MCP `set_assignee` を呼ぶ:
- `number`: 起動要因になった対象の番号
- `is_pr`: 対象が PR なら true

ここで待機に入るため、「ラベル除去」は実行しない（ユーザーの指示は応答ループで受ける）。

### ラベル除去

MCP `transition_phase` を呼ぶ:
- `number`: 起動要因になった対象の番号
- `is_pr`: 対象が PR なら true
- `remove_labels_`:
  - 自分の確認ラベル（`AI_MONITOR_LABEL_CONFIRM_*`）の値
- `add_labels_`: なし

### 作業完了報告

MCP `report_completion` を呼ぶ:
- `agent_name`: `{自分}`
- `number`: 起動要因になった対象の番号
