# ユーザー確認箇所

エージェントが手を止めてユーザーの応答を待つ箇所の一覧。
1 つの epic を最後まで通すとユーザーの操作が何回要るかを把握し、減らせる箇所を判断するために使う。

「待機」は `議論中` 付与 + `assignee=ユーザー` でターンを終える箇所を指す。
ユーザーが `議論中` を外すまでワークフローは進まないため、ここが実質的な所要時間を決める。

止まる箇所は 2 つの軸で数える。
「どこで止まるか」が待機の一覧、「1 回の停止が何往復に伸びるか」が応答ループの一覧。

| 種別 | 意味 |
| --- | --- |
| 承認 | 成果物の内容を確定させる。ユーザーが外さない限り先へ進まない |
| 選択 | 複数案から方針を選ばせる。答えが一意に定まる場合は質問せず前提として置く規約がある |
| 検収 | 後戻りできない操作（マージ・巻き戻し）の直前に置く最終確認 |
| 報告 | 回答・結果を提示して受領を待つ。判断は求めない |

## 応答ループ

待機に入った面でユーザーが修正を求めると、`議論中` が付いたまま assignee が外れて応答ループに入る。
応答ループは 1 回で終わるとは限らず、ユーザーが納得するまで「フィードバック → 反映 → 再待機」を繰り返す。
上の一覧が「何回止まるか」なら、こちらは「1 回の停止が何往復に伸びうるか」を示す。

応答ループを持つのは 13 エージェント・15 フェーズで、待機を作るほぼ全てのエージェントが対を持つ。

| エージェント | 応答ループのフェーズ | 起動条件 |
| --- | --- | --- |
| intake-issue-triager | 分解判定（応答ループ） | `議論中` あり + 未解決の自分宛コメントがある |
| system-conductor | 応答ループ | `議論中` あり + 未解決の自分宛コメントがある |
| system-architect | 応答ループ | `議論中` あり + 未解決の自分宛コメントがある |
| epic-conductor | 応答ループ | `議論中` あり + 未解決の自分宛コメントがある |
| epic-poc-runner | 応答ループ | `議論中` あり + 未解決の自分宛コメントがある |
| mock-designer | 方針の応答ループ | `議論中` あり + `### モック` 未記入 + 未解決の自分宛コメントがある |
| mock-designer | モックの応答ループ | `議論中` あり + `### モック` 記入済み + 未解決の自分宛コメントがある |
| complex-scenario-writer | 応答ループ | `議論中` あり + 未解決の自分宛コメントがある |
| story-conductor | 応答ループ | `議論中` あり + 未解決の自分宛コメントがある |
| single-scenario-writer | 応答ループ | `議論中` あり + 未解決の自分宛コメントがある |
| subsystem-conductor | 応答ループ | `議論中` あり + 未解決の自分宛コメントがある |
| architect | 応答ループ | `議論中` あり + 未応答のユーザー発言がある |
| questioner | 応答ループ | `議論中` あり + 未解決の自分宛コメントがある |
| resetter | 応答ループ | `議論中` あり + 未解決の自分宛コメントがある |

mock-designer だけ応答ループが 2 つある。
画面一覧の方針とモック HTML そのもので確認の対象が変わるため、`### モック` の記入有無で分けている。

architect の起動条件だけ「未応答のユーザー発言」で、他は「未解決の自分宛コメント」になっている。
設計提案がインラインコメントで、会話欄のコメントとは別に扱う必要があるため。

## レイヤーごとの回数

画面変更なし・PoC 不要の標準的な epic を、story 1 件 / subsystem 1 件 / 設計ページ 3 枚で通した場合の回数。

| レイヤー | シナリオ影響あり | シナリオ影響なし | 内訳 |
| --- | --- | --- | --- |
| intake | 1 | 1 | 分解判定 |
| epic | 2 | 0 | 要件確定（質問がある場合のみ）・複合シナリオ |
| story | 2 | 0 | 要件確定（質問がある場合のみ）・単一シナリオ |
| subsystem | 1 | 1 | SA とタスク一覧をまとめて 1 回 |
| 設計（architect） | 1 | 1 | 担当分の全ページをまとめて 1 回 |
| 合計 | 7 | 3 | 差し戻し・エスカレーションが起きるとさらに増える |

統合テストレビューは全 pass なら待機せず次へ渡すため、この数には入らない。
fail をシナリオ側の問題と判定したときだけ、修正内容の確認で待機する。

## 減らす方針

以下 5 つを減らすと決めた（実施済み）。
待機は標準的な epic で 11 回から 7 回、シナリオに影響しない修正では 3 回になる。

| 箇所 | 現状 | 変更後 |
| --- | --- | --- |
| architect の設計ページ確定 | ページ 1 枚ごとに待機する。ページ数がそのまま待機回数になる | subsystem 内の全ページを揃えてから 1 回だけ確認する |
| subsystem-conductor の SA とタスク一覧 | 2 段階で待機する | SA とタスク一覧を 1 コメントにまとめて 1 回にする |
| subsystem-conductor のマージ起動 | subsystem ごとに検収する | 検収を挟まず自動でマージする |
| epic / story-conductor の要件確定 | 質問が 0 件でも待機する | 質問が 0 件なら待機せず完了処理へ進む |
| epic / story レイヤーの素通し | 設計書の修正が無いレイヤーでも要件確定で待機する | 修正箇所が無ければ確認を挟まず下位レイヤーの起票まで進む。最短で subsystem の対応が始まる |

最後の 1 つが最も効く。
シナリオに影響しない修正では epic と story がユーザーを止めずに通り抜け、subsystem レイヤーだけがユーザーと会話する形になる。

減らさないもの:

| 箇所 | 残す理由 |
| --- | --- |
| intake の分解判定 | Issue の分け方はユーザーの意図そのもので、他に決められる材料がない |
| resetter の巻き戻し | 削除・クローズが後戻りできない |
| 各レイヤーのエスカレーション対応 | 上位へ上げるかの判断はユーザーの優先度に依存する |
| epic-poc-runner の PoC 結果・questioner の回答 | 判断を求めない報告で、回数も少ない |
