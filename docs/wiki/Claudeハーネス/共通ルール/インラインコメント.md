# インラインコメント

PR に commit を積んだら、待機に入る前に 3 種類のコメントを投稿する。
成果物のファイルだけでは、どこに判断があったのか・なぜその形にしたのかがユーザーに伝わらないため、行に紐づけて残す。

| 種類 | 投稿先 | 宛先 | 内容 |
| --- | --- | --- | --- |
| 確認事項 | 該当行にインライン | ユーザー | 選択肢が複数あり、ユーザーに決めてほしい判断 |
| 補足事項 | 該当行にインライン | なし | 確認は不要だが、その行だけでは意図が読み取れない背景 |
| 確認事項（全体） | 会話欄 | ユーザー | ファイルの特定箇所に紐づかない、進め方・スコープ・他ページとの整合の論点 |

3 種類とも形式上は任意だが、出さないとユーザーが判断できないため、迷ったら投稿する側に倒す。
1 論点 = 1 コメントで投稿し、複数の論点をまとめない。

## 確認事項（インライン）

論点 1 件ごとに MCP `create_review_comment` を呼ぶ:
- `pr_number`: 対象 PR の番号
- `path`: 対象ファイルのパス
- `line`: 論点にあたる行
- `sender`: 自分のエージェント名
- `receiver`: ユーザーログイン名（`gh api user --jq '.login'` で取得）
- `body`: その行で選んだ内容 + 他に取り得た選択肢 + 推奨（いま書いてある案）と理由

`receiver` を指定するとコメントに `@{ユーザー}` のメンション行が入る。
ユーザーに決めてほしいものは必ず `receiver` を付ける。

## 補足事項（インライン）

成果物を読み返し、次のような箇所を洗い出して残す。
下表は着眼点のヒントで、ここに載っているものだけを書く趣旨ではない。

| 観点 | 例 |
| --- | --- |
| 選択の理由 | なぜこの型 / この分割 / この順序にしたか |
| 見送った案 | 検討したが採らなかった実装とその理由 |
| 記述内容の意図 | その記述 / 設定値が何を狙っているか、変えると何が壊れるか |
| 前提と制約 | 依存ライブラリ・外部システム・上流設計から来ている制約 |
| 影響範囲 | この変更が他のどこに効くか・触ってはいけない箇所 |
| 既知の限界 | 今回のスコープ外にした条件・暫定対応である旨 |
| 参考資料 | 根拠にした設計書・外部ドキュメント・Issue / PR へのリンク |
| 上記以外 | 観点に当てはまらなくても、その行だけでは伝わらないと判断したこと |

補足 1 件ごとに MCP `create_review_comment` を呼ぶ:
- `pr_number`: 対象 PR の番号
- `path`: 対象ファイルのパス
- `line`: 補足したい行
- `sender`: 自分のエージェント名
- `body`: その行に対する補足（`receiver` は指定しない）

行だけでは伝わらないと少しでも思ったら書く。
量の上限は設けない。

## 確認事項（会話欄）

論点 1 件ごとに MCP `comment` を呼ぶ:
- `number`: 対象 PR の番号
- `is_pr`: true
- `sender`: 自分のエージェント名
- `receiver`: ユーザーログイン名
- `format`:
  - `type`: `plain`
  - `body`: 論点 + 他に取り得た選択肢 + 推奨と理由
