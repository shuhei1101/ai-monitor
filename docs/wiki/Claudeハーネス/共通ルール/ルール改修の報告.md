# ルール改修の報告

ルールに従って書いたのにユーザーから指摘を受けたら、その場でルール改修 Issue を起票する。

そのセッションで直して終わると、同じルールを読む別プロジェクト・別セッションが同じ指摘を受け続ける。
対象になるのはルール側の欠陥で、次の 2 つを扱う。

- ルールの記述が誤っている（記述どおりに書いた結果を否定された）
- ルールに記述が無い（判断の拠り所が無く、ユーザーの求める書き方と違う書き方をした）

自分がルールから外れていた場合は対象外（ルールは正しく、直すのは自分の成果物）。
手順書どおりに進められない事象は共通ルール『不具合の報告』の領分で、そちらとは別に扱う。

## 起票先

指摘の対象がどちらのルールかで MCP ツールを選ぶ。

| 指摘の対象 | MCP ツール |
| --- | --- |
| 言語 / フレームワークの規約（`docs/rules/` 配下） | `create_plugin_rule_issue` |
| 手順書 / 規約 / テンプレート（ai-monitor の `docs/wiki/` 配下） | `create_monitor_rule_issue` |

引数はどちらも同じで、次を渡す。

- `rule_page`: 対象ルールのページパス（起票先リポジトリ内の相対パス）
- `rule_excerpt`: 指摘の元になったルールの記述。記述が無いことが問題なら、無いと分かる書き方にする
- `title` / `body`: 何をどう直したいかと、指摘に至った経緯
- `agent_name` / `number`: 自分のエージェント名と、担当している Issue / PR の番号

## 報告した後

報告は自分の作業とは別に残る。
起票した Issue はユーザーが承認するまで動き出さないので、報告したこと自体を待たない。

- 指摘そのものへの対応（成果物の修正・返信）は通常どおり続ける
- 同じルールへの報告が既に上がっていても気にしない（重複の整理は intake-issue-triager が担う）
- 起票に失敗しても本来の作業は止めない
