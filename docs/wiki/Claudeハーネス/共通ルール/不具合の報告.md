# 不具合の報告

手順書のとおりに進められない事象に行き当たったら、その場で MCP `create_defect_issue` を呼んで ai-monitor へ報告する。

対象になるのは ai-monitor の仕組みそのものの欠陥。

- 実行中のフェーズの手順に、その状況で選べる分岐が無い
- 手順・規約・テンプレートの記述が互いに矛盾している
- MCP ツールが手順どおりの引数で想定外のエラーを返す

担当プロジェクトの要件・設計に関する論点は対象外で、そちらは指揮役へのエスカレーションで扱う。

## 報告の内容

- `source_pages` には原因になったページを Wiki ルートからの相対パス（`エージェント/{名前}/フェーズ/{フェーズ名}.md` / `規約/{名前}.md` 等）で並べる。
  手順書・規約・テンプレートのいずれでもよく、1 つの事象が複数ページにまたがっても Issue は分けない
- `body` には事象と再現の経緯を地の文と箇条書きで書く（見出しはツールが付けるため、本文側では作らない）
- `workaround` には取った回避策を書く。
  回避できずに作業を中断する場合は省略する（省略が「ワークフローが止まっている」の合図になる）

## 報告した後

報告は自分の作業とは別に残る。
起票した Issue はユーザーが承認するまで動き出さないので、報告したこと自体を待たない。

- 手順の意図から補って作業を完了できる場合、そのまま続行して次の担当へ引き継ぐ
- 完了できない場合、担当している Issue / PR に中断の報告コメント（起票した Issue へのリンク付き）を投稿し、`議論中` 付与 + assignee をユーザーにして待機する

## MCP サーバーが応答しないとき

特定のツールが引数を弾くのではなく、全ツールが `Unable to connect` を返すなどサーバー自体が応答しなくなった場合に限り、共通ルール『MCPツール名』の `gh` 禁則を解いて作業を続けてよい。
数分のリトライで復帰しないことを確かめてから切り替える。

`report_completion` は `gh` に相当が無いため、`処理中:{自分}` ラベルを `gh` で外して自ターンを終える。
セッションの生存時刻は更新できないが、処理中ラベルさえ外れていればモニターは次の周期で確認ラベルを見て通常どおり起動する。

復帰しないまま作業を完了できない場合は、上の「完了できない場合」の手順に合流する。
